Continuum — Start Here

The onboarding path, in order. Budget about 40 minutes to go from cold to productive.

The fastest orientation is the test suite. It runs offline on a mock LLM in under 20 seconds with no API key. Run it first — before reading anything — so you know the system works and you have a feedback loop for everything after.

What This Is

Continuum is a data layer for novels. Chapters go in; a queryable, spoiler-safe knowledge base comes out — characters, locations, objects, factions, relationships, plot threads, commitments, who-knows-what, and per-chapter continuity critiques. It is browsable as a React wiki and exposed to writing agents over MCP.

Continuum analyzes prose; it does not write it. The intended writer is an agent (e.g. Claude over the MCP server) that queries Continuum for ground truth while drafting, then saves finished chapters back.

The whole system is two spines over one database:

If you remember one invariant, make it this one: chapter raw_text is ground truth. Every projection can be deleted and rebuilt from it, which is why schema changes are survivable.

1. Run It

Assuming the repo is already set up on this machine (if not, jump to Full Setup and come back):

cd backend && .venv/bin/python -m pytest -q

Expected, and verified on main as of 2026-08-26:

457 passed, 3 skipped in 18.18s

That is 78 test files covering the whole write spine, read layer, critic, gate, and evals — all on a deterministic mock LLM with hash embeddings and a real Postgres. No network, no API key, no cost. Change anything in the codebase and you get a verdict in under 20 seconds.

The same two commands run in CI on every push and pull request (.github/workflows/ci.yml): the backend job spins up a pgvector/pgvector:pg16 service, applies the schema, and runs pytest; the frontend job runs lint, typecheck, and build. No provider credentials are involved — the suite is mock-LLM end to end.

Use backend/.venv, not the repo-root .venv. Running pytest from the repo root collects DB-integration tests that expect an initialized database and will fail for reasons that have nothing to do with your change. Always cd backend first.

What's Downstream

You do not need these to understand the system. Come back to them when you have a reason:

backend/api/routes/

20 route modules. They contain no SQL — enforced by contract tests. Each one is a thin translation of ?cap= into up_to_chapter.

frontend/src/routes/

26 wiki pages. React + react-query. Read useChapterCap.ts first; the cap is the only concept that isn't obvious.

backend/pipeline/critic/

5 deterministic continuity checks plus a runner. One critique per chapter, run for every caller; whether a FAIL blocks is the caller's policy.

backend/evals/

A golden 10-chapter fixture novel and an answer key. Critic precision/recall, retrieval recall_at_k, extraction fidelity, entity resolution.

Decisions to Know

Two choices shape the codebase in ways you'd otherwise have to reverse-engineer from commits.

Analyzer, not generator

A full chapter-authoring sub-system — scene planner, prose drafter, orchestrated revision loop — was built, briefly wired, and then deleted in full in July 2026 once the product decision landed on analyzer-only. It is not on the roadmap, and any reference to source='generated' you find in the commit history is history, not intent.

Refusing a write

This is the one place Continuum is more than a data layer. Every write runs the CRITIQUE phase before extraction — the same five checks, once, for every caller. What differs is what a FAIL costs, and that is the caller's on_continuity_fail policy rather than anything the pipeline infers about who is writing:

  • "warn" (the default — the CLI and the Process page): record the findings, ingest anyway. There is already a human at the keyboard.
  • "block" (asked for by the MCP save_chapter tool alone, because an agent writes unattended): refuse the write and park the draft in draft_submissions for review in the wiki's Review page.

An outage — the critique switched off, or running without a real model — refuses a blocking caller outright with nothing parked, because there is no verdict to record. A missing verdict is never a pass.

So a row in chapters written through save_chapter either passed continuity or was human-overridden through the Review queue with the blocking findings recorded on it. Rows from the un-blocking callers carry their findings without that guarantee — the invariant belongs to the policy, not to the row.

That is a policy enforcement point, and it is deliberate. Keeping the judgement caller-agnostic is what stops it drifting into two different notions of "consistent".

No-key demo: set USE_MOCK_LLM=true in backend/.env, start the API and frontend, and visit http://localhost:5173. Create a novel and process the text from backend/evals/golden/ch01.txt. Mock extraction exercises the application but does not measure model quality; MCP save_chapter refuses in this mode because no real continuity verdict is available. To serve the built UI from one process, run npm run build in frontend, then uv run novel-webapp in backend and visit http://127.0.0.1:8000.

The application assumes local, trusted access. Its API has no authentication and can modify and delete novels; a hosted deployment needs authentication.

Local Gotchas

Three things that will confuse you on day one.

Your active database may not be novel_wiki

backend/scripts/branch_db.sh gives each git branch its own database named novel_wiki_<branch_slug>, and writes a gitignored backend/.env.branch that pipeline/config.py loads after .env with override=true. So .env can say novel_wiki while you are actually reading and writing a branch database.

backend/scripts/branch_db.sh show    # which DB am I actually on?
backend/scripts/branch_db.sh list    # all novel_wiki_* databases
backend/scripts/branch_db.sh clear   # drop back to plain .env
Check this before you conclude your data is missing. A branch database can outlive the branch that created it, and .env.branch keeps pointing at it after you switch back to main. The script never writes to novel_wiki, and drop/reset refuse to operate on it — but nothing stops a stale .env.branch from quietly redirecting you.

Use the right virtualenv

backend/.venv (Python 3.11) is the project environment — that's what uv sync manages and what the test command above uses. The repo-root .venv is not it.

Eval numbers are plumbing checks, not quality claims

The eval harness runs on a deterministic mock LLM by default. The retrieval metric is reported as bm25_recall_at_k in that mode — real-embedding hybrid numbers only exist behind RUN_LLM_EVALS=1, and the harness comments say the mock number must never be quoted as hybrid.

Do not cite eval metrics from a mock run as system quality. They exist to catch regressions in the plumbing. See State of the System → Eval Metrics for what each number does and does not mean.
