Developer Reference

Detailed reference for the pipeline functions, database schema, API endpoints, and frontend patterns. Use this alongside the Architecture Overview, which explains the mental model and data flow.

Getting Started

Prerequisites

  • Python 3.11+
  • PostgreSQL 15+ with pgvector extension
  • Node 20+ (for frontend)
  • An API key for your LLM provider (e.g. OPENAI_API_KEY or GEMINI_API_KEY, matching DEFAULT_MODEL; or set USE_MOCK_LLM=true to skip)

Backend Setup

# Install dependencies
cd backend
pip install -e .

# Create and initialize the database
createdb novel_wiki
novel-pipeline init-db

# Or with a custom DB URL
DATABASE_URL=postgresql://user:pass@host/mydb novel-pipeline init-db

Run the API server

cd backend
uvicorn api.app:app --reload --port 8000

Frontend Setup

cd frontend
npm install
npm run dev        # dev server on :5173
npm run build      # builds to frontend/dist/ (served by FastAPI)

Process a chapter

# Via CLI
cd backend
novel-pipeline process-chapter \
  --novel-id <uuid> \
  --number 1 \
  --title "Chapter 1: The Beginning" \
  --file chapter1.txt

# Re-process (delete old extraction, then re-run)
novel-pipeline process-chapter \
  --novel-id <uuid> \
  --number 1 \
  --file chapter1.txt \
  --replace

# Via API (multipart form)
curl -X POST http://localhost:8000/api/novels/<novel_id>/process \
  -F "chapter_number=1" \
  -F "title=Chapter 1" \
  -F "text=@chapter1.txt"

Configuration

All settings live in backend/pipeline/config.py as a frozen dataclass. Values are read from environment variables (via python-dotenv).

Environment VariableDefaultDescription
DATABASE_URL postgresql://localhost/novel_wiki PostgreSQL connection string (psycopg3 format). Can be overridden per git branch: backend/scripts/branch_db.sh use writes a gitignored backend/.env.branch pointing at a branch-specific database, which pipeline/config.py loads with override=true (anchored to the backend/ directory, regardless of the process CWD). branch_db.sh clear reverts to plain .env.
OPENAI_API_KEY / GEMINI_API_KEY / … — Provider API key matching DEFAULT_MODEL, read directly from the environment by LiteLLM (not a config.py field). Required unless USE_MOCK_LLM=true
DEFAULT_MODEL gpt-4o-mini LiteLLM model string for all extraction passes
EMBEDDING_MODEL text-embedding-3-small LiteLLM embedding model
EMBEDDING_DIMENSIONS 1536 Vector dimensions. Must match what pgvector HNSW index was created with — init-db now asserts this against the live chapters.embedding column and exits with an explanatory error on drift, rather than letting every subsequent chapter die on an opaque ::vector cast failure.
CRITIC_ENABLED true Whether ingestion runs the continuity critic. For human writes it's a separate post-ingest judgement, not part of getting a chapter into the memory layer — set false for ingest-only deployments and run python -m pipeline.critic.cli later if you want the reports. Overridable per request via run_critic on POST /chapters/process. For agent writes (source='agent') it's load-bearing, not optional: the write gate runs the critic before extraction, and CRITIC_ENABLED=false refuses every agent write outright (reason: "critic_disabled") rather than letting them through uncritiqued — fail-closed, no override. See Architecture: The Agent Write Gate.
CRITIQUE_CLAIMS extract Where the critique phase gets its claims. extract spends one extra LLM call per chapter reading the chapter text via extract_draft_claims(), which is what gives the knowledge and location/possession checks anything to test — the extraction passes describe what characters learned and gained, never what they act on as already-known. reuse reuses the existing passes and skips the call, at the cost of those two checks never firing. Mock runs always fall back to reuse, since extract_draft_claims returns empty claims without a real LLM and an empty draft passes the critic vacuously.
DB_MAX_CONNECTIONS 20 Connection-pool ceiling. Every API route handler is a plain def, so Starlette runs them on its 40-slot threadpool; the previous hardcoded 5 made concurrent requests queue and then fail with PoolTimeout after psycopg's 30s default, surfacing as an unhandled 500.
LLM_TEMPERATURE 0.1 Temperature for all extraction LLM calls. Low = deterministic.
CHUNK_SIZE 2000 Tokens per chunk in sliding window
CHUNK_OVERLAP 200 Overlap tokens between adjacent chunks
USE_MOCK_LLM false Use regex mock instead of real LLM. Good for testing without API keys.
CANONICALIZER_MAX_ROSTER 80 Max roster entries serialized into one canonicalization LLM call (most string-similar kept). Bounds prompt cost as the cast grows; ≤ 0 disables the cap.
CONTEXT_MAX_CHARACTERS 40 Max characters injected into extraction prompts. Mentioned-in-chapter entities are always kept; the rest back-fills by recency. ≤ 0 disables the cap.
CONTEXT_MAX_LOCATIONS 30 Max locations injected into extraction prompts (same selection rules as characters).
RUN_LLM_EVALS unset Set to 1 to run evals/tests/test_extraction_fidelity.py::test_extraction_fidelity_real_llm, which ingests the golden fixture with a real LLM and spends API credits. Unset (default), that test is collected but skipped; the rest of evals/ runs offline against the mock LLM. See Eval Harness.
EMBEDDING_DIMENSIONS must be set before init-db. The schema.sql uses a __EMBEDDING_DIM__ placeholder that gets replaced at init time. If you change the dimension later, you need to drop and recreate the DB or rebuild the vector indexes.

Eval Harness backend/evals/

A hand-written golden fixture novel (backend/evals/golden/: 10 chapters plus answer_key.yaml) drives four offline evals plus two env-gated online evals, all runnable with cd backend && .venv/bin/python -m pytest evals/ -s (offline, mock LLM + a real Postgres). No API key or network access is required for the default run.

EvalModuleWhat It Measures
Scoring libraryevals/tests/test_scoring.pyPure unit tests for the name/interval/word-overlap matchers in evals/scoring.py — no DB.
Critic precision/recallevals/critic_eval.py, evals/tests/test_critic_eval.pySeeds known continuity violations and checks the ContinuityCritic flags every one, with no false positives on a clean draft.
Retrieval recall@kevals/harness.py::run_retrieval_eval, evals/tests/test_retrieval_eval.pyIngests the golden novel through analyze_chapter (mock LLM, hash embeddings, real chunking + Postgres FTS) once per module via the golden_novel fixture, then runs the 10 golden queries through the production reads.search.search() path and scores recall@8 against each query's expected chapter. Floor: mean recall@8 ≥ 0.9, raised from 0.5 on 2026-08-14 — the old floor was calibrated against the AND-semantics BM25 and query-cosine MMR that scored exactly 0.5, so it could not have caught that regression. Currently scores 1.00.
Extraction fidelityevals/harness.py::read_projections, evals/tests/test_extraction_fidelity.pyMock-mode run only checks the ingest → projections → scoring plumbing (no thresholds — canned mock extraction won't match the answer key). The real-LLM variant, gated behind RUN_LLM_EVALS=1 (see the env-var table above), asserts recall floors: characters/locations ≥ 0.75, objects ≥ 1.0, possessions ≥ 0.6, knowledge ≥ 0.5.
Entity resolutionevals/er_eval.py::run_resolution_eval, evals/tests/test_er_eval.pyGrades surface-form → entity assignment against the answer key's resolution: alias sets using scoring.pairwise_resolution (every unordered pair of surfaces is one same-entity-or-not judgement, so the two id spaces need not correspond). Reports false_merges and missed_merges separately because the costs are not symmetric, plus coverage for surfaces extraction never emitted — those are extraction misses, not resolution errors, and are excluded from precision/recall. Mock mode checks plumbing only; the RUN_LLM_EVALS=1 variant fails on any false merge and asserts recall ≥ 0.6, type accuracy ≥ 0.8, and zero cross-type duplicates.
Duplicate-pair countevals/er_eval.py::count_duplicate_pairsGround-truth-free diagnostic, so it runs against any ingested novel, not just the fixture. Scores every entity pair with the canonicalizer's own _name_pair_similarity at its own LEXICAL_MATCH_RATIO and splits the result same-type vs cross-type. Candidates, not confirmed duplicates — Mr. Bennet/Mrs. Bennet scores 0.95 and is two people — so read the pair list, not just the count.
Cross-type duplicates: found and repairable, not yet prevented. EntityCanonicalizer._load_roster loads candidates one entity_type at a time, so it never compares a character against an object. On a 3-chapter real-LLM ingest this was the dominant failure mode: 14 cross-type duplicate pairs against 1 same-type across 63 entities.

merge_entities used to raise unless source and target shared an entity_type, which left these unrepairable from either direction. It now treats a cross-type merge as a reclassification: entity-level references (relationships, shared_dynamics, canon_facts, commitments, state_deltas) repoint as usual; event involvement moves from the source's involved_* column into the target's; and the source's type-specific rows (character_states, knows_edges, possesses_edges) die with its typed row, since they were artifacts of the misclassification. The non-cascading FKs — scenes.pov_character_id, scenes.location_id, character_states.location_id, locations.parent_location_id — are explicitly detached first, or the delete raises a foreign-key violation. Covered by pipeline/db/tests/test_entity_merge_integration.py against real Postgres, because the fake-DB tests assert which statements run and cannot catch an FK violation.

Still missing: cross-type candidate loading in the canonicalizer, so these are caught by review rather than prevented at ingest.
RUN_LLM_EVALS=1 .venv/bin/python -m pytest evals/ runs the real-LLM extraction-fidelity and entity-resolution evals in addition to the offline suite — they spend API credits and are not part of the default test run.

MCP Server novel-mcp

backend/mcp_server/ is a FastMCP stdio server (entry point novel-mcp, see the scripts table above) that exposes the data layer to writing agents in place of the retired per-domain query CLI. It's registered for this repo via the root .mcp.json (uv run --directory backend novel-mcp); see the repo README.md's "Writing agents (MCP)" section for Claude Code (anywhere) and Claude Desktop setup.

Cutoff-aware, with no exceptions. Every lookup below takes a writing_chapter and returns only facts from chapters strictly before it — an agent drafting chapter N sees the world as of N−1. list_novels is the sole tool without a cutoff, because it is not chapter-anchored.
list_chapters and canon_facts leaked unwritten chapters prior to 2026-08-16. list_chapters accepted no writing_chapter at all and passed up_to_chapter=None, which resolves to MAX(number); since reads.chapters.list_chapters selects summary_long, an agent calling it "for orientation" on chapter 12 of a 40-chapter novel received long-form summaries of the entire remaining plot. canon_facts had the same defect one notch softer — its writing_chapter was optional and defaulted to the unsafe value. Both now require the parameter and cap at writing_chapter − 1, matching every other tool. Regression guards live in mcp_server/tests/test_server.py.
timeline_events was non-functional prior to 2026-07-12 — it queried a timeline table that doesn't exist in the schema and always returned an UndefinedTable error dict. It's now backed by reads.timeline.list_timeline() (story events grouped by chapter, the same data the /api/novels/{id}/timeline route serves) and requires writing_chapter like every other cutoff-aware tool.

A revision aid, not the enforcement point — save_chapter runs the same checks itself and will refuse a draft that fails them regardless of whether this was called first, so skipping it doesn't let a bad draft through GEN
save_chapternovel_id, chapter_number, text, title=Nonen/aIngests a finished draft as source="agent". Gated (added 2026-08-24): before extraction runs, the continuity critic critiques the raw draft; a FAIL, a critic error, or a disabled critic (CRITIC_ENABLED=false) refuses the write instead of ingesting. Refusal returns {ingested: false, status, submission_id, reason: "fail"|"critic_error"|"critic_disabled", fails: [...], warns: [...]}. For reason: "fail" or "critic_error" the draft is parked and status is "pending_review" with a real submission_id — revise against fails and resubmit; a resubmission supersedes the parked draft. For reason: "critic_disabled" nothing is parked (there is no verdict to record): status is "refused" and submission_id is null — this is an outage, not a verdict, so hold the text and retry later. A clean pass returns the pre-existing success contract, {ingested: true, chapter_id, materialized, critique} — materialized: false or critique: null means the corresponding best-effort post-commit phase failed and needs a manual re-run. Still refuses to overwrite an existing chapter (replace=False), independent of the gate. Note: the tool hardcodes use_mock_llm=None, so exercising this path (gate or extraction) always makes real LLM calls GEN
Suggested agent workflow: open_threads + unresolved_commitments + get_character → draft → check_continuity → revise → save_chapter.

analyze_chapter()

Main pipeline orchestration function in backend/pipeline/pipeline.py. Renamed from process_chapter (2026-07-12); the CLI subcommand is still process-chapter (hyphenated, unchanged).

def analyze_chapter( *, novel_id: str, chapter_number: int, raw_text: str, chapter_title: str | None, use_mock_llm: bool | None, chunk_size: int, chunk_overlap: int, progress: Any | None = None, db: DBClient | None = None, replace: bool = False, source: str = "human" ) → dict[str, Any]
novel_idstrThe novel to process this chapter under
chapter_numberintChapter number (1-indexed). Must be unique per novel unless replace=True.
raw_textstrFull raw chapter text
chapter_titlestr | NoneDisplay title for this chapter
use_mock_llmbool | NoneUse deterministic mock LLM (for tests/dev). None uses real LLM.
chunk_sizeintToken size of each sliding-window chunk
chunk_overlapintToken overlap between adjacent chunks
progressAny | NoneOptional progress callback object with on_pass_start/on_pass_done methods
dbDBClient | NoneInjectable DB client. If None, a new DBClient is created and closed on exit.
replaceboolIf True, delete all previously extracted data for this chapter before re-processing. Default False.
sourcestrProvenance tag stored on the chapter row (e.g. "human", "agent"). Default "human".
Duplicate check happens before LLM extraction. If the chapter already exists and replace=False, a ValueError is raised immediately — no LLM calls are made.
Transactional persistence. All DB writes (ingest, entities, events, relationships, summaries, scenes, knows-edges, commitments) run inside a single client.session() transaction. The LLM extraction and canonicalization phases run outside the transaction; only persistence is atomic.

Return value

Beyond the extraction-count fields (chapter_id, chunks, summary_preview, new_characters, new_locations, events, state_deltas, thread_updates, continuity_flags), the result dict carries two keys for the phases that run after persistence commits:

materializedboolPhase 4. True if StateMaterializer ran successfully for this novel up to the latest chapter.
critiquedict | NonePhase 5. Summary of the continuity critique: {novel_id, chapter_number, passed, total_findings, fails, warns, by_check}. None if the critique phase raised.
Phases 4/5 run outside the persistence transaction. Materialization (phase 4, StateMaterializer) and the continuity critique (phase 5, ContinuityCritic + persist_critique) execute after the client.session() block has already committed the chapter. Each is wrapped in its own try/except and logs on failure rather than raising — a failure in either phase leaves the chapter fully saved; it only shows up as materialized: False or critique: None in the result, and requires a manual re-run (pipeline.state.cli for materialization) to catch up. Every analyzed chapter gets a persisted critique — one row in critique_reports (unique per chapter_id) plus per-finding rows in critique_findings (severity = fail | warn | info).

load_story_context()

Called at the start of analyze_chapter() to build the context string injected into every LLM prompt. Fetches:

  • All existing character names (for entity recognition)
  • All existing location names
  • Open plot threads (title + description)
  • Recent events from the last 3 chapters (up to 200)
  • Custom entity lists per registered type

_persist_extraction()

Writes a fully resolved extraction result to the DB. Called once per chapter inside the session transaction. Receives a DBSession (not a DBClient).

Writes to (in order): characters, locations, factions, objects, entities (custom), character_states, relationships (with chapter_id), shared_dynamics, events, plot_threads, thread_events, continuity_flags.

The relationships INSERT now carries a chapter_id column, enabling cascade deletion when replace=True re-processes a chapter.

Mock Extractor

When settings.use_mock_llm=True, the extractor uses regex-based entity detection (capitalized words) and sentence splitting instead of LLM calls. Output follows the same schema but is low-quality — fine for integration testing.

IntraExtractionDeduplicator

Lives in backend/pipeline/extraction/canonicalizer.py.

Runs after merge_extractions() and before entity resolution. Uses a single LLM call to group name variants within the current extraction and rename all occurrences to the longest canonical form.

class IntraExtractionDeduplicator:
  def deduplicate( extracted: dict, chapter_text: str ) → dict

Rule: longest form wins. "Jane" + "Jane Bennet" → "Jane Bennet" everywhere in the extraction dict.

One focused LLM call per entity type with ≥ 2 extracted names — the four built-in types plus any custom types found in custom_entities. Renames are applied to every name field: new_entities, entity_deltas, events (characters, locations, objects, factions), relationship_updates, dynamics_updates, scenes (POV, location, present characters), learnings (learner, source, shared-with), and custom_entities. Lists are de-duplicated after renaming.

Why longest wins? A longer form is almost always more specific and less ambiguous. "Miss Bennet" could be any Bennet sister; "Elizabeth Bennet" is unambiguous. The LLM groups the variants, Python picks the longest from each group.
Hallucination guard: group members returned by the LLM are validated (case-insensitively) against the names actually present in the extraction. Invented names are discarded, so a hallucinated "canonical" form can never overwrite real extracted names.

EntityCanonicalizer

Same file. Cross-chapter dedup: matches extracted names against the existing DB roster.

class EntityCanonicalizer:
  def canonicalize( chapter_text: str, candidate_names_by_type: dict[str, set[str]] ) → dict[str, dict[str, str]]

Per entity type, in order:

StepWhat happensLLM cost
1. Known filterCandidates exactly matching a roster name/alias (case-insensitive) are droppedNone
2. Deterministic mergenormalize_name() equality (case, whitespace, surrounding punctuation/quotes, leading article) against exactly one roster entry → alias written directly. Ambiguous normalized matches are deferred to the LLMNone
3. LLM resolutionOne call per type with remaining candidates. Roster capped at CANONICALIZER_MAX_ROSTER (default 80) most string-similar entries1 call/type

Validation before a merge is accepted is tiered by evidence. Characters require a verbatim grammatical_anchor quoted from the chapter text. Other types (including custom types) make the merge permanent — candidate appended to the target's aliases[], which the EntityResolver alias lookup later finds — only when there is a valid anchor or the names are lexically close (token subset like "the Empire" ⊂ "The Galactic Empire", or high sequence similarity) and the candidate is close to no other roster entry — an ambiguous shorthand must not be welded to whichever entity the LLM picked. A merge justified by reasoning alone (a required schema field, so its presence proves nothing) does not write the alias; instead the pipeline applies it as a rename to the current extraction, so the merge takes effect this chapter while a hallucinated alias can't permanently reroute every future mention of that name.

EntityResolver

Lives in backend/pipeline/extraction/resolver.py.

class EntityResolver:
  def resolve_character(name: str) → UUID
  def resolve_location(name: str) → UUID
  def resolve_faction(name: str) → UUID
  def resolve_object(name: str) → UUID
  def resolve_custom_entity(name: str, entity_type: str) → UUID
  def resolve_any_entity(name: str) → UUID

All resolve methods return a UUID — either an existing entity's UUID or a newly created one. They never return None. The resolver maintains an in-memory cache per instance (one instance per pipeline run).

resolve_location folds sub-locations into their parent when parent_location is set in entity metadata. If metadata["parent_location"] is non-empty, the parent name is resolved (or created) instead of the sub-location, preventing floor/corridor/room entries from polluting the locations table. The sub-location's name is appended to the parent's aliases, so later metadata-less resolutions of the same name (event and scene resolution) fold to the same row instead of creating a standalone duplicate; a newly created parent does not inherit the sub-location's description.

Resolution cascade

StepMethodCreates new?
1. In-memory cache(entity_type, lowercased name) hit from earlier in the same runNo
2. Name or aliasOne combined query: case-insensitive match on name or aliases[], name matches taking priority (LIKE wildcards in names are escaped)No
3. Partial matchCharacters only: "Jane" matches "Jane Bennet" on a word boundary, adds "Jane" as aliasNo
4. Create newINSERT into entities + specific tableYes

resolve_custom_entity resolves against the entities table by exact name or entities.aliases (written by the canonicalizer), creating an entities-only row when nothing matches. Custom types extracted with an unregistered or differently-cased type are normalized (or dropped) in analyze_chapter before they reach the resolver.

resolve_any_entity lookup order: entities table by name or alias → each typed table (character, faction, location, object) by name or alias → only then fall back to creating a character. The typed-alias step matters: without it, a relationship that references "the Empire" (an alias of faction "The Galactic Empire") would create a phantom character named "the Empire".

EmbeddingService

Lives in backend/pipeline/embeddings.py.

class EmbeddingService:
  def embed_text(text: str) → list[float]
  def _hash_embedding(text: str) → list[float]

embed_text() calls LiteLLM's embedding endpoint. If the call fails or use_mock_llm=True, it falls back to _hash_embedding(), which generates a deterministic pseudo-random vector from the SHA-256 hash of the text. Hash embeddings are meaningless for semantic search but let the pipeline complete without an API key.

embed_chapter_and_events()

Batch-embeds the chapter summary and all event descriptions for a processed chapter. Updates chapters.embedding and events.embedding in the DB. Called after _persist_extraction().

persist_extras SOTA

Lives in backend/pipeline/extraction/persist_extras.py. Populates the SOTA tables added on the closing-the-gap-with-sota branch — scenes, knows_edges, commitments — plus the multi-granularity summary columns on chapters. Called from analyze_chapter inside the persistence transaction, after _persist_extraction().

persist_scenes()

persist_scenes(db, *, chapter_id, scenes_data: list[dict], resolver: EntityResolver, embedder: EmbeddingService) → list[str]

Inserts scene rows (upserting on (chapter_id, scene_index)) and returns the inserted/updated scene ids. Each scene dict has: pov_character_name, location_name, time_anchor (free text), present_character_names (name list), summary. POV and present characters resolve reference-only (create=False) so a scene can't mint a phantom character; the resolver converts names to UUIDs. summary is embedded via embedder for scene search.

persist_knows_edges()

persist_knows_edges(db, *, chapter_number, learnings: list[dict], resolver: EntityResolver) → list[str]

Inserts who-knows-what edges from the knowledge_state_deltas pass's learnings list. Each learning dict: character_name, fact_description, source_type (one of dialogue | observation | inference | witnessed | told | assumed — anything else is stored as NULL), certainty (high/medium/low or a raw 0.0–1.0 float), shared_with_character_names. The knowing character resolves reference-only; a learning naming an unknown character is skipped.

persist_commitments()

persist_commitments(db, *, novel_id, chapter_number, foreshadows: list[dict], payoffs: list[dict], resolver: EntityResolver, embedder: EmbeddingService) → dict[str, list[str]]

Two independent jobs in one call, matching the extractor's foreshadows_introduced / payoffs_delivered split. Foreshadows insert as new commitments rows with status='pending'. Payoffs are matched against this novel's currently-pending commitments by fuzzy text similarity (difflib.SequenceMatcher on the payoff's matches_foreshadow text against each candidate's foreshadow_text, falling back to the payoff text itself at a lower weight) — a match below a 0.45 similarity floor is dropped rather than forced, and each matched commitment updates to status='satisfied' with payoff_chapter/payoff_text set. Returns {"inserted": [...], "satisfied": [...]} commitment ids. There is currently no path to broken or abandoned — those are set only by hand via the canon API pattern, or default to whatever a user picks in the UI.

persist_multi_summaries()

persist_multi_summaries(db, *, chapter_id, summary_short, summary_medium, summary_long, embedder: EmbeddingService | None = None)

Updates chapters.summary_short, chapters.summary_long, and (via COALESCE(NULLIF(...))) the legacy chapters.summary column from summary_medium. When embedder is given and summary_medium is non-empty, also re-embeds chapters.embedding from the medium summary — this is why analyze_chapter skips its own chapter-embedding call whenever a medium summary exists (see analyze_chapter()).

DBClient / DBSession

Lives in backend/pipeline/db/client.py. Wraps a psycopg_pool.ConnectionPool and exposes a small query API (execute, fetchone, fetchall, fetchval, execute_many). Used as a context manager (with DBClient() as db:) — __exit__ closes the pool.

DBClient.session()

DBClient.session() → contextmanager[DBSession]

Yields a DBSession bound to one pooled connection. All statements issued through the session run on that single connection and therefore inside one implicit transaction. On a clean exit the connection is committed; on any exception it is rolled back and the exception is re-raised.

analyze_chapter() uses session() for its entire persistence phase — every write (ingest, entities, events, relationships, summaries, scenes, knows-edges, commitments) is atomic. The LLM extraction and canonicalization phases run outside the transaction, and the phase-4 materialize / phase-5 critique steps run after it commits.

DBSession

A thin wrapper around a single psycopg connection. Exposes the same query methods as DBClient (execute, fetchone, fetchall, fetchval). The commit= keyword argument accepted by those methods is silently ignored — commit/rollback ownership stays with the enclosing DBClient.session() context manager. This means existing persistence helpers work unchanged whether they receive a DBClient or a DBSession.

Usage pattern: 
with DBClient() as db:
    with db.session() as s:
        helper_a(s, ...)   # same connection
        helper_b(s, ...)   # same connection, same transaction
# committed if no exception, rolled back otherwise

Schema: relationships

CREATE TABLE relationships (
  id              UUID   PRIMARY KEY DEFAULT gen_random_uuid(),
  entity_a_id     UUID   NOT NULL REFERENCES entities,
  entity_b_id     UUID   NOT NULL REFERENCES entities,
  rel_type        TEXT   NOT NULL,  -- SINGLE value enforced: 'ally', 'enemy', 'mentor', etc.
  from_chapter    INT,
  to_chapter      INT,
  notes           TEXT,
  sentiment       FLOAT,           -- SOTA: -1.0 to 1.0
  evidence_event_ids UUID[],        -- SOTA: events that established this
  superseded_by_id   UUID,          -- SOTA: points to newer relationship row
  "symmetric"     BOOLEAN,          -- NULL = unjudged; reserved word, see below
  created_at      TIMESTAMPTZ DEFAULT now()
);

Note: rel_type is a single text value per row — not an array. The extractor is constrained to output one rel_type per relationship (enforced in extraction prompts after commit 1af7156).

When a relationship changes (e.g., allies become enemies), a new row is inserted with superseded_by_id pointing from the old row to the new one. This creates a linked-list history of relationship evolution.

entity_a_id/entity_b_id order encodes direction, but for inherently mutual rel_types (spouse_of, sibling_of, ...) that order carries no meaning — and even labels that usually read as mutual (friend_of, rival_of) can be one-sided in a given story (A considers B a friend; B doesn't reciprocate). A label-only lookup can't tell these apart, so the extractor judges it per instance: the relationship_updates prompt (prompts.py) asks the model to set symmetric to true only when both sides genuinely hold the relationship (or it's true by definition), false when it reflects one entity's unreciprocated view, and leave it null when the text doesn't say. When the text shows the two sides genuinely differing, the extractor emits two rows — one per entity's actual stance — rather than one shared label.

symmetric is nullable because older rows predate this field and the extractor sometimes has no signal either way. The API resolves the displayed value via backend/reads/relationship_types.py::resolve_symmetric(rel_type, stored_symmetric): it trusts a non-null stored value, and otherwise falls back to a static label allowlist (is_symmetric()) for a reasonable default. This computed boolean is returned alongside every relationship row and graph edge; the frontend uses it to show a neutral "↔" instead of "to"/"from" and to drop the arrowhead in the graph views.

Writing this column requires quoting it. SYMMETRIC is a fully reserved PostgreSQL keyword (it comes from BETWEEN SYMMETRIC), not merely a DDL-context one, so any bare use as an identifier is a parse error — including the column list of an INSERT/UPDATE. It parses unquoted in only two places: after a dot (SELECT r.symmetric) and as an AS label. That asymmetry is why the read paths in reads/ look unquoted while schema.sql and the relationship insert in pipeline/pipeline.py write "symmetric". Real-Postgres coverage lives in pipeline/extraction/tests/test_persist_relationships_integration.py; the fake-DB tests record statement text without parsing it and cannot catch this class of bug.

Schema: canon_facts SOTA

CREATE TABLE canon_facts (
  id               UUID        PRIMARY KEY DEFAULT gen_random_uuid(),
  novel_id         UUID        NOT NULL REFERENCES novels,
  kind             TEXT        NOT NULL,   -- 'identity', 'world_rule', 'relationship', 'object_property'
  subject_entity_id UUID       REFERENCES entities,
  predicate        TEXT        NOT NULL,   -- e.g. "is_heir", "has_curse"
  value            TEXT        NOT NULL,   -- e.g. "true", "Ironwood Throne"
  source_chapter   INT,
  confidence       FLOAT       NOT NULL DEFAULT 1.0,
  locked           BOOLEAN     NOT NULL DEFAULT false,
  created_at       TIMESTAMPTZ DEFAULT now()
);

When locked=true, a contradicting extraction does not overwrite the fact — instead a continuity_flag of type canon_contradiction is raised. When locked=false, a new extraction value replaces the old one. The frontend Canon page shows these grouped by subject entity and lets users toggle the lock.

canon_facts pass schema

The canon_facts extraction pass (pass 13) asks the LLM to emit a list of facts. Each fact in the extracted array has the following shape: 

{
  "kind": "identity" | "world_rule" | "relationship" | "object_property",
  "subject_name": "...",          // entity name — resolved to subject_entity_id
  "predicate": "is_heir",           // snake_case property key
  "value": "true",                  // string value (booleans as "true"/"false")
  "confidence": 0.95               // 0.0–1.0
}

persist_canon_facts() upserts on (novel_id, subject_entity_id, predicate). If the existing row has locked=true, the value is not updated; instead a continuity_flags row is inserted with flag_type='canon_contradiction' describing the conflict.

Canon API Endpoints

MethodPathBody / ParamsReturns
GET /api/novels/{id}/canon ?cap=N&locked_only=true CanonFactRow[] — id, kind, subject_name, predicate, value, source_chapter, confidence, locked. cap is optional; omit for every fact regardless of source_chapter.
POST /api/novels/{id}/canon {"kind": "...", "predicate": "...", "value": "...", "subject_entity_id": "uuid|null", "confidence": 0.9, "locked": false} {"id": "uuid"} — HTTP 201
PATCH /api/novels/{id}/canon/{fact_id} {"locked": true} or {"value": "..."} or both {"ok": true} — HTTP 200. Partial update: only supplied fields are changed.

Lock semantics: PATCH with {"locked": true} marks the fact as authoritative. Subsequent extraction passes that would change the value will instead emit a continuity_flag (flag_type='canon_contradiction'). PATCH with {"locked": false} unlocks it, restoring normal upsert behaviour.

  id          UUID   PRIMARY KEY DEFAULT gen_random_uuid(),
  report_id   UUID   NOT NULL REFERENCES critique_reports ON DELETE CASCADE,
  check_name  TEXT   NOT NULL,
  severity    TEXT   NOT NULL, -- CHECK IN (fail, warn, info)
  message     TEXT   NOT NULL,
  quote       TEXT,

  version     INT         NOT NULL,
  applied_at  TIMESTAMPTZ DEFAULT now()
);

state_deltas is the extraction-time event log for state — the tier-2, immutable, cascade-deleted rows the State Materializer replays into character_states and the bitemporal edges. ordinal orders rows within a chapter because created_at can't: now() is transaction-stable, so every row a single chapter's extraction pass writes gets the same timestamp.

critique_reports / critique_findings persist one continuity-critique result per chapter instead of discarding it after the request. schema_version holds a single row, rewritten on every init-db run, so client code can check what schema it's talking to. It's currently 2, bumped from 1 by draft_submissions below (added 2026-08-24, the agent write gate). There is no migration tool: schema.sql is idempotent (CREATE TABLE IF NOT EXISTS / ADD COLUMN IF NOT EXISTS throughout), so an existing database upgrades by re-running uv run novel-pipeline init-db — it picks up the new table and re-stamps schema_version without touching data in any other table.

CREATE TABLE draft_submissions (
  id                UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  novel_id          UUID NOT NULL REFERENCES novels ON DELETE CASCADE,
  chapter_number    INTEGER NOT NULL,
  title             TEXT,
  raw_text          TEXT NOT NULL,
  status            TEXT NOT NULL DEFAULT 'pending', -- CHECK IN (pending, accepted, rejected)
  findings          JSONB NOT NULL,
  submitted_at      TIMESTAMPTZ DEFAULT now(),
  resolved_at       TIMESTAMPTZ,

);

A parked agent draft that failed the continuity gate (pipeline/gate.py) before it ever reached extraction. findings holds {fails: [...], warns: [...]} (each a serialized Finding — check, severity, message, quote, suggested_fix, context), or {fails: [], warns: [], error: "..."} when the row exists because the critic itself threw rather than returned a verdict. This table is deliberately outside the cutoff-aware read contract — reads/drafts.py is the one module in reads/ exempt from taking up_to_chapter, because a parked draft is not canon and has no point-in-time semantics. Resubmitting a draft for the same (novel_id, chapter_number) supersedes (not deletes) the prior pending row: it's marked rejected with resolution_note = 'superseded by resubmission' in the same transaction that inserts the new one. Returns CustomEntityDetail — id, name, entity_type, description, relationships[]. cap filters the relationships sub-list: a relationship is hidden when COALESCE(from_chapter, provenance chapter) is beyond the cap — rows whose extractor left from_chapter NULL fall back to the chapter that asserted them (relationships.chapter_id), the same rule every relationship read uses.
POST /api/novels/{novel_id}/entities/merge — Merge a duplicate entity into its canonical twin. Body: {"source_entity_id": uuid, "target_entity_id": uuid} (universal entity ids). Repoints every reference in one transaction, absorbs the source's name+aliases as target aliases, deletes the source. Source and target may differ in entity_type — that case is treated as a reclassification and the target's type wins; see Entity Merge for what survives. Response includes cross_type and source_entity_type. 400 on same-id or missing entity.
GET /api/novels/{novel_id}/entities/duplicates — Duplicate-looking entity pairs for review before merging, split cross_type_pairs / same_type_pairs (each with score, kind, and both sides' entity_id/type/name). Scored with the canonicalizer's own _name_pair_similarity at its own LEXICAL_MATCH_RATIO, so a listed pair is one the canonicalizer would have called a match had it compared them. Not chapter-capped — a duplicate created in chapter 40 is still one you want to see. Candidates, not confirmed duplicates: Mr. Bennet/Mrs. Bennet scores 0.95 and is two people.

API: Search

MethodPathQuery Params
GET /api/novels/{id}/search ?q=&cap=N&k=8

Hybrid (semantic + keyword) search over chapters, scenes, and events, capped at cap. q is required and non-empty; k is clamped to 1–50 (default 8). API: Plot Threads

MethodPathQuery Params
GET /api/novels/{id}/threads ?cap=N&status=open|closed|all

Returns PlotThread[] each with a thread_events: ThreadEventLink[] array. Each row carries both the raw status/closed_chapter columns (the novel-wide truth) and a derived status_at_cutoff: a thread closed in a chapter later than cap reads as progressing, not closed, at that cutoff — closed_chapter itself is not nulled out. A thread only counts as closed when its raw status is still closed (a thread reopened by a later chapter reads by its live status; the ingest upsert also clears closed_chapter on reopen), and a closed thread with no closed_chapter anchor counts as closed only in an uncapped view — a capped view cannot date the closure, so it reads progressing. The same unanchored-terminal rule applies to commitments (broken/abandoned read pending in capped views) and continuity flags (a resolution with no resolved_chapter_id counts only uncapped); see reads.common.resolve_cutoff_and_uncapped. The status query param filters on status_at_cutoff. Threads.tsx displays status_at_cutoff as the primary badge and shows raw status only as a muted "(closes ch N)" hint when the two differ.

API: Entity Graph

MethodPathQuery Params
GET /api/novels/{id}/entity-graph ?cap=N

Returns EntityGraph: {"nodes": EntityGraphNode[], "edges": EntityGraphEdge[]}.

Returns a unified story graph including all entity types (characters, locations, factions, custom types, etc.). Edge sources:

  • Relationship edges (edge_kind: "relationship") — from the relationships table. Rendered as solid blue arrows labelled with rel_type; the arrowhead is dropped when the edge's computed symmetric flag is true (mutual relationship types like spouse_of).
  • Dynamic edges (edge_kind: "dynamic") — from shared_dynamics. Rendered as dashed gray lines; hover shows story moment description.
  • Event edges (edge_kind: "event") — co-occurrence from events (character↔character and character→location). Rendered as dashed gray lines; hover shows event description(s).
  • Possession/location edges (edge_kind: "possession", "location") — from possesses_edges and located_in_edges; wired for future data.

Multiple records between the same entity pair from the same source are collapsed into one story edge (tooltip shows all descriptions). At most two edges per pair: one relationship + one story edge. Each edge carries optional edge_kind and tooltip fields.

Node colours (AAA-accessible palette). Nodes are tinted by entity type with bright, high-luminance hues so each fill clears WCAG non-text contrast against the dark canvas and stays distinguishable: characters #60a5fa (blue), locations #34d399 (green), objects #fbbf24 (amber), factions #c084fc (purple), custom types #22d3ee (cyan). Node and edge labels render in light text (#e2ddef) with a dark halo — ~13:1 contrast — so names stay legible even where they overlap a node. Colour is never the only cue: every node and legend pill is also text-labelled.

API: Draft Review Queue GATE

backend/api/routes/drafts.py, backing the wiki's Review page (/novels/{id}/review). These are the human side of the agent write gate — see Architecture: The Agent Write Gate for how a row ends up in draft_submissions in the first place, and the schema above for the row shape.

MethodPathBody / QueryReturns
GET /api/novels/{id}/drafts ?status=pending|accepted|rejected|all (default pending) DraftSummary[] — id, novel_id, chapter_number, title, status, fail_count, warn_count, submitted_at, resolved_at, resolution_note. Newest first.
GET /api/novels/{id}/drafts/pending-count — PendingCount — {pending: N}
GET /api/drafts/{submission_id} — DraftDetail — DraftSummary plus raw_text, findings ({fails: [...], warns: [...]}, or with an error key on a critic_error row). 404 if not found.
POST /api/drafts/{submission_id}/accept AcceptRequest: {note?, edited_text?} Ingests the draft as canon via pipeline/drafts.py::accept_submission — the only caller allowed to bypass the gate. Runs the full pipeline (not just an insert), so it costs a real extraction. Pass edited_text to ingest a human-revised version instead of the original raw_text; whenever it's present the resolution note is annotated "(edited before ingest)" (the Review page only sends it once the textarea contents actually diverge from raw_text, so this reads accurately in practice, but the check itself is client-side). The draft's blocking findings are written through to continuity_flags as accepted_override:<check> rows rather than discarded. Returns {accepted: true, chapter_id, flags_written}. 404 if not found, 409 if already resolved. Raises RuntimeError (500) if the chapter ingests successfully but the findings write-through / status update then fails — the chapter is on record but the submission is stuck at pending; that needs manual resolution, not a retry (a retry hits the duplicate-chapter guard).
POST /api/drafts/{submission_id}/reject ResolveRequest: {note?} Marks the draft rejected. Nothing is ingested; the agent must revise and resubmit via save_chapter. Returns {rejected: true, submission_id}. 404 if not found, 409 if already resolved.
No sidebar badge. The Review Queue nav link (Sidebar.tsx) is a plain link, not a count badge — count_pending exists in reads/drafts.py and the pending-count endpoint above serves it, but nothing in the sidebar calls it yet. That wiring was scoped out, not missed.

Frontend: Query Pattern

All server data fetching uses @tanstack/react-query. The pattern is consistent across all 24 page components: 

import { useQuery } from '@tanstack/react-query';
import { useParams } from 'react-router-dom';
import { useChapterCap } from '../hooks/useChapterCap';
import { api } from '../api';

export function Scenes() {
  const { novelId } = useParams();
  const cap = useChapterCap();

  const { data, isLoading, error } = useQuery({
    queryKey: ['scenes', novelId, cap],
    queryFn: () => api.scenes(novelId!, cap),
    enabled: !!novelId,
  });

  if (isLoading) return <p>Loading...</p>;
  if (error) return <p>Error loading scenes.</p>;
  return <SceneTable scenes={data ?? []} />;
}

The queryKey array includes cap so React Query refetches automatically when the chapter cap slider changes.

Frontend: Adding a New Page

Checklist for adding a new wiki page:

  1. Add the API function to api.ts (fetch + TypeScript type)
  2. Create the route component in src/routes/MyPage.tsx
  3. Add the route to App.tsx under the novel layout
  4. Add the nav link to Sidebar.tsx
  5. Use useChapterCap() and pass cap to the API call
  6. Add cap to the React Query queryKey
