Developer Reference

Detailed reference for the pipeline functions, database schema, API endpoints, and frontend patterns. Use this alongside the Architecture Overview, which explains the mental model and data flow.

Getting Started

Prerequisites

  • Python 3.11+
  • PostgreSQL 15+ with pgvector extension
  • Node 20+ (for frontend)
  • An OpenAI API key (or set USE_MOCK_LLM=true to skip)

Backend Setup

# Install dependencies
cd backend
pip install -e .

# Create and initialize the database
createdb novel_wiki
python -m pipeline --init-db

# Or with a custom DB URL
DATABASE_URL=postgresql://user:pass@host/mydb python -m pipeline --init-db

Run the API server

cd backend
uvicorn api.app:app --reload --port 8000

Frontend Setup

cd frontend
npm install
npm run dev        # dev server on :5173
npm run build      # builds to frontend/dist/ (served by FastAPI)

Process a chapter

# Via CLI
cd backend
novel-pipeline process-chapter \
  --novel-id <uuid> \
  --number 1 \
  --title "Chapter 1: The Beginning" \
  --file chapter1.txt

# Re-process (delete old extraction, then re-run)
novel-pipeline process-chapter \
  --novel-id <uuid> \
  --number 1 \
  --file chapter1.txt \
  --replace

# Via API (multipart form)
curl -X POST http://localhost:8000/api/novels/<novel_id>/process \
  -F "chapter_number=1" \
  -F "title=Chapter 1" \
  -F "text=@chapter1.txt"

MCP Server novel-mcp

backend/mcp_server/ is a FastMCP stdio server (entry point novel-mcp, see the scripts table above) that exposes the data layer to writing agents in place of the retired per-domain query CLI. It's registered for this repo via the root .mcp.json (uv run --directory backend novel-mcp); see the repo README.md's "Writing agents (MCP)" section for Claude Code (anywhere) and Claude Desktop setup.

Cutoff-aware by default. Every lookup below takes a writing_chapter and returns only facts from chapters strictly before it — an agent drafting chapter N sees the world as of N−1. The exceptions are timeline_events (timeline rows aren't chapter-anchored; its docstring warns callers about spoilers) and canon_facts, list_novels, list_chapters (no cutoff parameter at all).

process_chapter()

Main pipeline orchestration function in backend/pipeline/pipeline.py.

def process_chapter( *, novel_id: str, chapter_number: int, raw_text: str, chapter_title: str | None, use_mock_llm: bool | None, chunk_size: int, chunk_overlap: int, progress: Any | None = None, db: DBClient | None = None, replace: bool = False, source: str = "human", generation_meta: dict | None = None ) → dict[str, Any]
novel_idstrThe novel to process this chapter under
chapter_numberintChapter number (1-indexed). Must be unique per novel unless replace=True.
raw_textstrFull raw chapter text
chapter_titlestr | NoneDisplay title for this chapter
use_mock_llmbool | NoneUse deterministic mock LLM (for tests/dev). None uses real LLM.
chunk_sizeintToken size of each sliding-window chunk
chunk_overlapintToken overlap between adjacent chunks
progressAny | NoneOptional progress callback object with on_pass_start/on_pass_done methods
dbDBClient | NoneInjectable DB client. If None, a new DBClient is created and closed on exit.
replaceboolIf True, delete all previously extracted data for this chapter before re-processing. Default False.
sourcestrProvenance tag stored on the chapter row (e.g. "human", "generated"). Default "human".
generation_metadict | NoneArbitrary JSON metadata stored on the chapter row (e.g. model name, temperature). Default None.
Duplicate check happens before LLM extraction. If the chapter already exists and replace=False, a ValueError is raised immediately — no LLM calls are made.
Transactional persistence. All DB writes (ingest, entities, events, relationships, summaries, scenes, knows-edges, commitments) run inside a single client.session() transaction. The LLM extraction and canonicalization phases run outside the transaction; only persistence is atomic.

load_story_context()

Called at the start of process_chapter() to build the context string injected into every LLM prompt. Fetches:

  • All existing character names (for entity recognition)
  • All existing location names
  • Open plot threads (title + description)
  • Recent events from the last 3 chapters (up to 200)
  • Custom entity lists per registered type

_persist_extraction()

Writes a fully resolved extraction result to the DB. Called once per chapter inside the session transaction. Receives a DBSession (not a DBClient).

Writes to (in order): characters, locations, factions, objects, entities (custom), character_states, relationships (with chapter_id), shared_dynamics, events, plot_threads, thread_events, continuity_flags.

The relationships INSERT now carries a chapter_id column, enabling cascade deletion when replace=True re-processes a chapter.

Mock Extractor

When settings.use_mock_llm=True, the extractor uses regex-based entity detection (capitalized words) and sentence splitting instead of LLM calls. Output follows the same schema but is low-quality — fine for integration testing.

IntraExtractionDeduplicator

Lives in backend/pipeline/extraction/canonicalizer.py.

Runs after merge_extractions() and before entity resolution. Uses a single LLM call to group name variants within the current extraction and rename all occurrences to the longest canonical form.

class IntraExtractionDeduplicator:
  def deduplicate( extracted: dict, chapter_text: str ) → dict

Rule: longest form wins. "Jane" + "Jane Bennet" → "Jane Bennet" everywhere in the extraction dict.

One focused LLM call per entity type with ≥ 2 extracted names — the four built-in types plus any custom types found in custom_entities. Renames are applied to every name field: new_entities, entity_deltas, events (characters, locations, objects, factions), relationship_updates, dynamics_updates, scenes (POV, location, present characters), learnings (learner, source, shared-with), and custom_entities. Lists are de-duplicated after renaming.

Why longest wins? A longer form is almost always more specific and less ambiguous. "Miss Bennet" could be any Bennet sister; "Elizabeth Bennet" is unambiguous. The LLM groups the variants, Python picks the longest from each group.
Hallucination guard: group members returned by the LLM are validated (case-insensitively) against the names actually present in the extraction. Invented names are discarded, so a hallucinated "canonical" form can never overwrite real extracted names.

EntityCanonicalizer

Same file. Cross-chapter dedup: matches extracted names against the existing DB roster.

class EntityCanonicalizer:
  def canonicalize( chapter_text: str, candidate_names_by_type: dict[str, set[str]] ) → dict[str, dict[str, str]]

Per entity type, in order:

StepWhat happensLLM cost
1. Known filterCandidates exactly matching a roster name/alias (case-insensitive) are droppedNone
2. Deterministic mergenormalize_name() equality (case, whitespace, surrounding punctuation/quotes, leading article) against exactly one roster entry → alias written directly. Ambiguous normalized matches are deferred to the LLMNone
3. LLM resolutionOne call per type with remaining candidates. Roster capped at CANONICALIZER_MAX_ROSTER (default 80) most string-similar entries1 call/type

Validation before a merge is accepted is tiered by evidence. Characters require a verbatim grammatical_anchor quoted from the chapter text. Other types (including custom types) make the merge permanent — candidate appended to the target's aliases[], which the EntityResolver alias lookup later finds — only when there is a valid anchor or the names are lexically close (token subset like "the Empire" ⊂ "The Galactic Empire", or high sequence similarity) and the candidate is close to no other roster entry — an ambiguous shorthand must not be welded to whichever entity the LLM picked. A merge justified by reasoning alone (a required schema field, so its presence proves nothing) does not write the alias; instead the pipeline applies it as a rename to the current extraction, so the merge takes effect this chapter while a hallucinated alias can't permanently reroute every future mention of that name.

EntityResolver

Lives in backend/pipeline/extraction/resolver.py.

class EntityResolver:
  def resolve_character(name: str) → UUID
  def resolve_location(name: str) → UUID
  def resolve_faction(name: str) → UUID
  def resolve_object(name: str) → UUID
  def resolve_custom_entity(name: str, entity_type: str) → UUID
  def resolve_any_entity(name: str) → UUID

All resolve methods return a UUID — either an existing entity's UUID or a newly created one. They never return None. The resolver maintains an in-memory cache per instance (one instance per pipeline run).

resolve_location folds sub-locations into their parent when parent_location is set in entity metadata. If metadata["parent_location"] is non-empty, the parent name is resolved (or created) instead of the sub-location, preventing floor/corridor/room entries from polluting the locations table. The sub-location's name is appended to the parent's aliases, so later metadata-less resolutions of the same name (event and scene resolution) fold to the same row instead of creating a standalone duplicate; a newly created parent does not inherit the sub-location's description.

Resolution cascade

StepMethodCreates new?
1. In-memory cache(entity_type, lowercased name) hit from earlier in the same runNo
2. Name or aliasOne combined query: case-insensitive match on name or aliases[], name matches taking priority (LIKE wildcards in names are escaped)No
3. Partial matchCharacters only: "Jane" matches "Jane Bennet" on a word boundary, adds "Jane" as aliasNo
4. Create newINSERT into entities + specific tableYes

resolve_custom_entity resolves against the entities table by exact name or entities.aliases (written by the canonicalizer), creating an entities-only row when nothing matches. Custom types extracted with an unregistered or differently-cased type are normalized (or dropped) in process_chapter before they reach the resolver.

resolve_any_entity lookup order: entities table by name or alias → each typed table (character, faction, location, object) by name or alias → only then fall back to creating a character. The typed-alias step matters: without it, a relationship that references "the Empire" (an alias of faction "The Galactic Empire") would create a phantom character named "the Empire".

EmbeddingService

Lives in backend/pipeline/embeddings.py.

class EmbeddingService:
  def embed_text(text: str) → list[float]
  def _hash_embedding(text: str) → list[float]

embed_text() calls LiteLLM's embedding endpoint. If the call fails or use_mock_llm=True, it falls back to _hash_embedding(), which generates a deterministic pseudo-random vector from the SHA-256 hash of the text. Hash embeddings are meaningless for semantic search but let the pipeline complete without an API key.

embed_chapter_and_events()

Batch-embeds the chapter summary and all event descriptions for a processed chapter. Updates chapters.embedding and events.embedding in the DB. Called after _persist_extraction().

DBClient / DBSession

Lives in backend/pipeline/db/client.py. Wraps a psycopg_pool.ConnectionPool and exposes a small query API (execute, fetchone, fetchall, fetchval, execute_many). Used as a context manager (with DBClient() as db:) — __exit__ closes the pool.

DBClient.session()

DBClient.session() → contextmanager[DBSession]

Yields a DBSession bound to one pooled connection. All statements issued through the session run on that single connection and therefore inside one implicit transaction. On a clean exit the connection is committed; on any exception it is rolled back and the exception is re-raised.

process_chapter() uses session() for its entire persistence phase — every write (ingest, entities, events, relationships, summaries, scenes, knows-edges, commitments) is atomic. The LLM extraction and canonicalization phases run outside the transaction.

DBSession

A thin wrapper around a single psycopg connection. Exposes the same query methods as DBClient (execute, fetchone, fetchall, fetchval). The commit= keyword argument accepted by those methods is silently ignored — commit/rollback ownership stays with the enclosing DBClient.session() context manager. This means existing persistence helpers work unchanged whether they receive a DBClient or a DBSession.

Usage pattern: 
with DBClient() as db:
    with db.session() as s:
        helper_a(s, ...)   # same connection
        helper_b(s, ...)   # same connection, same transaction
# committed if no exception, rolled back otherwise

Schema: novels

CREATE TABLE novels (
  id          UUID        PRIMARY KEY DEFAULT gen_random_uuid(),
  title       TEXT        NOT NULL,
  author      TEXT,
  language    TEXT        NOT NULL DEFAULT 'en',
  created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);

Top-level container. Every other table scopes to a novel_id. A novel is just a name — the text lives in chapters.

Schema: chapters

CREATE TABLE chapters (
  id              UUID         PRIMARY KEY DEFAULT gen_random_uuid(),
  novel_id        UUID         NOT NULL REFERENCES novels,
  number          INT          NOT NULL,                    -- 1-indexed
  title           TEXT,
  raw_text        TEXT         NOT NULL,
  summary         TEXT,                                        -- medium summary
  summary_short   TEXT,                                        -- 1-2 sentence
  summary_long    TEXT,                                        -- detailed
  style_fingerprint TEXT,                                     -- author's voice notes
  embedding       vector(__EMBEDDING_DIM__),                    -- pgvector
  processed_at    TIMESTAMPTZ,
  source          TEXT         NOT NULL DEFAULT 'human',      -- provenance tag: 'human' | 'generated' | ...
  generation_meta JSONB,                                        -- arbitrary metadata (model, temperature, etc.)
  created_at      TIMESTAMPTZ  NOT NULL DEFAULT now(),
  UNIQUE(novel_id, number)
);

The __EMBEDDING_DIM__ placeholder is replaced with EMBEDDING_DIMENSIONS from config at init-db time. The summary / summary_short / summary_long fields support three different granularities for different UI use cases. source stores provenance ("human" for user-supplied text, "generated" for LLM-authored text, or any custom tag); generation_meta stores arbitrary JSON (e.g. model name, temperature) and is NULL for human-sourced chapters.

Schema: entities

CREATE TABLE entities (
  id          UUID     PRIMARY KEY DEFAULT gen_random_uuid(),
  novel_id    UUID     NOT NULL REFERENCES novels,
  entity_type TEXT     NOT NULL,
  name        TEXT     NOT NULL,
  aliases     TEXT[]   DEFAULT '{}',
  UNIQUE(novel_id, entity_type, name)
);

The universal entity table. Every character, location, faction, object, and user-defined custom entity gets a row here first. The 4 hardcoded types (character, location, faction, object) also get a row in their dedicated table. User-defined types (e.g. realm, deity) live only in this table — no dedicated table. The CHECK constraint on entity_type was removed to allow arbitrary type values from novel_entity_types. The aliases[] column holds canonicalizer-confirmed name variants for custom entity types (built-in types keep aliases on their dedicated tables); migration: pipeline.db.migrate_add_entities_aliases.

The relationships table references entities(id) so cross-type relationships (character→realm, character→faction) all work with the same join.

Schema: novel_entity_types

CREATE TABLE novel_entity_types (
  id          UUID     PRIMARY KEY DEFAULT gen_random_uuid(),
  novel_id    UUID     NOT NULL REFERENCES novels ON DELETE CASCADE,
  name        TEXT     NOT NULL,
  description TEXT,
  UNIQUE(novel_id, name)
);

Stores user-defined entity type definitions per novel. Created at novel-creation time via the genre-preset picker or manual entry. The pipeline reads these at extraction time to inject the custom type schema into the LLM prompt.

Genre presets (LitRPG, High Fantasy, Xianxia, Sci-Fi, Contemporary) seed the picker with recommended types for each genre. Each preset provides name and description for the LLM to understand what to extract.

-- State snapshot per chapter
CREATE TABLE character_states (
  id              UUID   PRIMARY KEY DEFAULT gen_random_uuid(),
  character_id    UUID   NOT NULL REFERENCES characters,
  chapter_id      UUID   NOT NULL REFERENCES chapters,
  location_id     UUID   REFERENCES locations,

Schema: events

CREATE TABLE events (
  id                  UUID     PRIMARY KEY DEFAULT gen_random_uuid(),
  chapter_id          UUID     NOT NULL REFERENCES chapters,
  description         TEXT     NOT NULL,
  event_type          TEXT,    -- 'action', 'revelation', 'conflict', 'dialogue', etc.
  impact_level        TEXT,    -- 'low', 'medium', 'high', 'critical'
  involved_characters UUID[],  -- references characters(id)
  involved_locations  UUID[],  -- references locations(id)
  involved_objects    UUID[],  -- references objects(id)
  involved_factions   UUID[],  -- references factions(id)
  subject_entity_id   UUID,    -- SOTA: primary subject
  verb                TEXT,    -- SOTA: action verb (e.g., "betrayed")
  object_entity_id    UUID,    -- SOTA: primary object
  story_time_ordinal  INT,     -- SOTA: story-time ordering (not narrative order)
  narrative_order     INT,     -- SOTA: order in which event appears in text
  scene_id            UUID,    -- SOTA: which scene this event belongs to
  embedding           vector(__EMBEDDING_DIM__),
  created_at          TIMESTAMPTZ DEFAULT now()
);

Events are the backbone of the timeline view. The involved_* UUID arrays allow querying "all events involving character X" via = ANY(involved_characters). These are GIN-indexed for fast containment queries.

story_time_ordinal vs narrative_order: Stories can tell events out of order (flashbacks, reveals). story_time_ordinal is when it happened in the story world. narrative_order is when the reader encountered it.

Schema: relationships

CREATE TABLE relationships (
  id              UUID   PRIMARY KEY DEFAULT gen_random_uuid(),
  entity_a_id     UUID   NOT NULL REFERENCES entities,
  entity_b_id     UUID   NOT NULL REFERENCES entities,
  rel_type        TEXT   NOT NULL,  -- SINGLE value enforced: 'ally', 'enemy', 'mentor', etc.
  from_chapter    INT,
  to_chapter      INT,
  notes           TEXT,
  sentiment       FLOAT,           -- SOTA: -1.0 to 1.0
  evidence_event_ids UUID[],        -- SOTA: events that established this
  superseded_by_id   UUID,          -- SOTA: points to newer relationship row
  symmetric       BOOLEAN,          -- NULL = unjudged; see below
  created_at      TIMESTAMPTZ DEFAULT now()
);

Note: rel_type is a single text value per row — not an array. The extractor is constrained to output one rel_type per relationship (enforced in extraction prompts after commit 1af7156).

When a relationship changes (e.g., allies become enemies), a new row is inserted with superseded_by_id pointing from the old row to the new one. This creates a linked-list history of relationship evolution.

entity_a_id/entity_b_id order encodes direction, but for inherently mutual rel_types (spouse_of, sibling_of, ...) that order carries no meaning — and even labels that usually read as mutual (friend_of, rival_of) can be one-sided in a given story (A considers B a friend; B doesn't reciprocate). A label-only lookup can't tell these apart, so the extractor judges it per instance: the relationship_updates prompt (prompts.py) asks the model to set symmetric to true only when both sides genuinely hold the relationship (or it's true by definition), false when it reflects one entity's unreciprocated view, and leave it null when the text doesn't say. When the text shows the two sides genuinely differing, the extractor emits two rows — one per entity's actual stance — rather than one shared label.

symmetric is nullable because older rows predate this field and the extractor sometimes has no signal either way. The API resolves the displayed value via backend/api/relationship_types.py::resolve_symmetric(rel_type, stored_symmetric): it trusts a non-null stored value, and otherwise falls back to a static label allowlist (is_symmetric()) for a reasonable default. This computed boolean is returned alongside every relationship row and graph edge; the frontend uses it to show a neutral "↔" instead of "to"/"from" and to drop the arrowhead in the graph views.

Schema: canon_facts SOTA

CREATE TABLE canon_facts (
  id               UUID        PRIMARY KEY DEFAULT gen_random_uuid(),
  novel_id         UUID        NOT NULL REFERENCES novels,
  kind             TEXT        NOT NULL,   -- 'identity', 'world_rule', 'relationship', 'object_property'
  subject_entity_id UUID       REFERENCES entities,
  predicate        TEXT        NOT NULL,   -- e.g. "is_heir", "has_curse"
  value            TEXT        NOT NULL,   -- e.g. "true", "Ironwood Throne"
  source_chapter   INT,
  confidence       FLOAT       NOT NULL DEFAULT 1.0,
  locked           BOOLEAN     NOT NULL DEFAULT false,
  created_at       TIMESTAMPTZ DEFAULT now()
);

When locked=true, a contradicting extraction does not overwrite the fact — instead a continuity_flag of type canon_contradiction is raised. When locked=false, a new extraction value replaces the old one. The frontend Canon page shows these grouped by subject entity and lets users toggle the lock.

canon_facts pass schema

The canon_facts extraction pass (pass 13) asks the LLM to emit a list of facts. Each fact in the extracted array has the following shape: 

{
  "kind": "identity" | "world_rule" | "relationship" | "object_property",
  "subject_name": "...",          // entity name — resolved to subject_entity_id
  "predicate": "is_heir",           // snake_case property key
  "value": "true",                  // string value (booleans as "true"/"false")
  "confidence": 0.95               // 0.0–1.0
}

persist_canon_facts() upserts on (novel_id, subject_entity_id, predicate). If the existing row has locked=true, the value is not updated; instead a continuity_flags row is inserted with flag_type='canon_contradiction' describing the conflict.

Canon API Endpoints

MethodPathBody / ParamsReturns

Lock semantics: PATCH with {"locked": true} marks the fact as authoritative. Subsequent extraction passes that would change the value will instead emit a continuity_flag (flag_type='canon_contradiction'). PATCH with {"locked": false} unlocks it, restoring normal upsert behaviour.

Two tables tracking "who was where" and "who had what" over time.

CREATE TABLE possesses_edges (
  id               UUID    PRIMARY KEY DEFAULT gen_random_uuid(),
  character_id     UUID    NOT NULL REFERENCES characters,
  object_id        UUID    NOT NULL REFERENCES objects,
  since_chapter    INT     NOT NULL,
  until_chapter    INT,
  evidence_event_id UUID   REFERENCES events,
  certainty        FLOAT   NOT NULL DEFAULT 1.0,
  superseded_by_id UUID
);

To find where entity X is "right now" (at cap chapter N): 

SELECT * FROM located_in_edges
WHERE entity_id = X
  AND since_chapter <= N
  AND (until_chapter IS NULL OR until_chapter > N)
ORDER BY since_chapter DESC LIMIT 1;

API: Entity Graph

MethodPathQuery Params
GET /api/novels/{id}/entity-graph ?cap=N

Returns EntityGraph: {"nodes": EntityGraphNode[], "edges": EntityGraphEdge[]}.

Returns a unified story graph including all entity types (characters, locations, factions, custom types, etc.). Edge sources:

  • Relationship edges (edge_kind: "relationship") — from the relationships table. Rendered as solid blue arrows labelled with rel_type; the arrowhead is dropped when the edge's computed symmetric flag is true (mutual relationship types like spouse_of).
  • Dynamic edges (edge_kind: "dynamic") — from shared_dynamics. Rendered as dashed gray lines; hover shows story moment description.
  • Event edges (edge_kind: "event") — co-occurrence from events (character↔character and character→location). Rendered as dashed gray lines; hover shows event description(s).
  • Possession/location edges (edge_kind: "possession", "location") — from possesses_edges and located_in_edges; wired for future data.

Multiple records between the same entity pair from the same source are collapsed into one story edge (tooltip shows all descriptions). At most two edges per pair: one relationship + one story edge. Each edge carries optional edge_kind and tooltip fields.

Node colours (AAA-accessible palette). Nodes are tinted by entity type with bright, high-luminance hues so each fill clears WCAG non-text contrast against the dark canvas and stays distinguishable: characters #60a5fa (blue), locations #34d399 (green), objects #fbbf24 (amber), factions #c084fc (purple), custom types #22d3ee (cyan). Node and edge labels render in light text (#e2ddef) with a dark halo — ~13:1 contrast — so names stay legible even where they overlap a node. Colour is never the only cue: every node and legend pill is also text-labelled.

Frontend: Query Pattern

All server data fetching uses @tanstack/react-query. The pattern is consistent across all 23 page components: 

import { useQuery } from '@tanstack/react-query';
import { useParams } from 'react-router-dom';
import { useChapterCap } from '../hooks/useChapterCap';
import { api } from '../api';

export function Scenes() {
  const { novelId } = useParams();
  const cap = useChapterCap();

  const { data, isLoading, error } = useQuery({
    queryKey: ['scenes', novelId, cap],
    queryFn: () => api.scenes(novelId!, cap),
    enabled: !!novelId,
  });

  if (isLoading) return <p>Loading...</p>;
  if (error) return <p>Error loading scenes.</p>;
  return <SceneTable scenes={data ?? []} />;
}

The queryKey array includes cap so React Query refetches automatically when the chapter cap slider changes.
