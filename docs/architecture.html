Continuum

A novel continuity engine that reads raw chapter text, extracts structured knowledge via LLM, and stores it in PostgreSQL so authors and readers can query anything — "where was Asha in chapter 3?", "what commitments are still unresolved?", "who knows the secret?". The result is a living wiki that grows chapter by chapter.

Ingest

Raw chapter text → chunked, sent to LLM with story context

Extract

13-pass LLM extraction of entities, events, threads, flags, scenes, dynamics, knowledge, commitments, canon facts

Query

25+ wiki-style views served by FastAPI, rendered in React — including entity graph, scenes, canon facts, and custom entity types

Active branch: closing-the-gap-with-sota — This branch added SOTA narrative-tracking tables (scenes, commitments, canon_facts, knows_edges, bitemporal edges), plus the Entity Graph with rich edges, Custom Entity Types with genre presets, and the Critic / Planner / Retrieval / State sub-modules.

Mental Model

Think of Continuum as a ETL pipeline for fiction. It does for novels what a data warehouse does for business events — continuously ingests raw narrative text and produces a structured, queryable knowledge graph.

The Pipeline (Write Path)

Chapter text → LLM extracts facts → deduplication → entity resolution → PostgreSQL. Everything flows in one direction. Nothing is updated retroactively.

The API (Read Path)

React frontend asks FastAPI for wiki views. All queries are "as-of chapter N" (the chapter cap), so you can time-travel without storing snapshots.

Three Layers of Abstraction

LayerWhat lives hereKey constraint
Entities Characters, locations, factions, objects, and user-defined custom types — the nouns of the story Every entity gets a UUID in the entities table first
Events Timestamped story events — the verbs. Now enriched with SVO triples and story-time ordering. Always tied to a chapter; can reference any entity type via UUID arrays
State Character state snapshots, scenes, relationships, knowledge edges, bitemporal possession/location edges Every state row has a chapter reference → enables chapter-cap filtering
Key insight: There are no "current state" columns anywhere. State is always derived by querying up to a chapter cap. This is the design that enables spoiler-free browsing.

Pipeline Overview

The pipeline lives in backend/pipeline/pipeline.py. The entry point for processing a chapter is process_chapter(). Here's the full flow:

  1. Ingest raw text — ingest_chapter() inserts the raw chapter text into the chapters table. Duplicate (novel_id, chapter_number) is rejected.
  2. Load story context — load_story_context() fetches existing characters, locations, open plot threads, recent events, and custom entity types from the DB. Characters and locations are selected, not dumped: entities whose name or alias appears in the chapter text always make the cut, the remainder back-fills by recency, and the lists are capped at CONTEXT_MAX_CHARACTERS (default 40) / CONTEXT_MAX_LOCATIONS (default 30) so prompt size stays bounded as the cast grows. The result is injected into every LLM prompt so the model knows what already exists.
  3. Chunk the text — sliding_window_chunks() splits the chapter into 2,000-token windows with 200-token overlap using tiktoken (falls back to whitespace split). Each chunk is processed independently.
  4. LLM extraction (13 passes per chunk) — ChapterExtractor runs 13 sequential LLM calls per chunk. See Extraction Passes for details.
  5. Merge across chunks — merge_extractions() deduplicates the results from all chunks by name/description (naïve string matching at this stage; objects are keyed by name + owner so same-named items with different owners survive the merge).
  6. Intra-extraction deduplication — IntraExtractionDeduplicator makes one focused LLM call per entity type (including the novel's custom types) to group name variants ("Jane", "Jane B", "Miss Bennet") and renames every occurrence to the longest canonical form — across new entities, deltas, events (characters, locations, objects, and factions), relationships, dynamics, scenes, learnings, and custom entities. Group members are validated against the actually-extracted names, so an LLM-hallucinated name can never become the canonical form. Renamed lists are also de-duplicated in place.
  7. Cross-chapter canonicalization — EntityCanonicalizer matches names not yet in the DB against the per-type roster. Names whose normalized form (normalize_name(): case, whitespace, surrounding punctuation, leading article) equals exactly one roster name/alias merge deterministically with zero LLM cost; only the rest go to one LLM call per type, with the roster capped to the CANONICALIZER_MAX_ROSTER (default 80) most string-similar entries so prompt size stays bounded as the novel grows. Matches confirmed by strong evidence (a verbatim anchor, or unambiguous lexical closeness for non-characters) are appended to the entity's aliases[] — custom entity types store theirs on entities.aliases; reasoning-only matches are instead applied as a rename to the current extraction (no permanent alias), so the merge still takes effect this chapter.
  8. Entity resolution — EntityResolver maps every entity name to an existing DB entity (exact name → alias → character partial-name match → create new). Returns UUIDs. Only the new_entities pass is allowed to create characters; every other pass resolves with create=False (resolve-or-skip) so a name it merely references can't mint a phantom character.
  9. Persist to DB — _persist_extraction() writes entities, events, relationships, shared dynamics, plot threads, continuity flags. It never writes character_states: state changes go through the typed state_deltas log instead, and character_states is the sole responsibility of the State Materializer, which runs at the end of process_chapter.
  10. Persist state deltas — persist_state_deltas() (persist_deltas.py) writes the state_deltas extraction pass into the state_deltas table: reference-only resolution (create=False) for the subject character, and for possession/location kinds the object/location too, so a delta naming an unknown entity is dropped rather than minting one. Rows carry subject_id/object_id as universal entities.id and location_id as the typed locations.id, with an ordinal preserving narrative order within the chapter — this is the tier-2 log the state materializer replays.
  11. Embed — embed_chapter_and_events() generates vector embeddings for each event description, plus the chapter summary only when no medium summary exists (otherwise persist_multi_summaries() embeds the chapter from summary_medium, so the extra call is skipped).
  12. Persist SOTA extras — persist_multi_summaries(), persist_scenes(), persist_knows_edges(), persist_commitments(), persist_canon_facts() fill the newer tables added in the SOTA branch. Canon facts upsert unless locked — a locked fact contradicted by extraction becomes a continuity_flag (flag_type='canon_contradiction') rather than an overwrite.
Note on idempotency: Re-processing a chapter requires passing replace=True (API: "replace": true in the ProcessRequest body). Without it, ingest rejects duplicate chapter numbers. With replace=True, delete_chapter_data() removes the following chapter-scoped derived rows before re-processing begins:
  • events, scenes, character_states, continuity_flags, shared_dynamics — deleted by chapter_id
  • relationships rows that carry a chapter_id (i.e. those written during this chapter's ingest)
  • knows_edges and commitments keyed by chapter number — deleted by chapter_number
Entity rows introduced by the chapter (characters, locations, factions, objects, entities) and plot-thread upserts are not deleted — they survive and are resolved against on re-processing, so entity identity remains stable across replace runs.

13 Extraction Passes

Each pass is a separate LLM call. The schema for what each pass returns is in prompts.py → PASS_SCHEMAS. The order matters — later passes can reference entities found in earlier ones via the merged context.

# Pass Name What It Extracts DB Target
1 chapter_summary One-sentence chapter summary chapters.summary
2 new_entities New characters, locations (with parent_location), factions, objects (with owner_name + distinguishing_properties), and custom entities (genre-specific types defined per novel) characters, locations, factions, objects, entities (for custom types)
3 state_deltas Typed state changes: possession gain/loss, location moves, knowledge learned, status updates (emotional_state/goals/physical_state/appearance/notes) — each with a verbatim evidence quote state_deltas (folded into character_states and the bitemporal edges by the materializer)
4 events Narrative events with type, impact level, involved entities events
5 thread_updates Plot thread open/progress/close with linked events plot_threads, thread_events
6 continuity_flags Foreshadowing, setups, callbacks, planted details continuity_flags
7 relationship_updates Entity-to-entity relationship arcs with type, direction, chapter range relationships
8 dynamics_updates Chapter-level snapshots of how two entities interact (tone, tension). Multiple updates for the same pair in one chapter (in either order) are merged into a single row — descriptions concatenated — to satisfy the one-row-per-pair-per-chapter unique constraint shared_dynamics
9 scene_segmentation Scene boundaries with POV character, location, time anchor, present characters scenes
10 multi_granularity_summaries Summary at three granularities: short (tweet), medium (paragraph), long (recap) chapters.summary_short, summary_medium, summary_long
11 knowledge_state_deltas Who learns what, certainty, how it was learned, who it was shared with knows_edges
12 commitments Foreshadow → payoff pairs (Chekhov's guns), trigger predicates, weight commitments
13 canon_facts Lockable world-facts: kind, subject entity, predicate, value, confidence. Upserts on (novel_id, subject_entity_id, predicate) — skips update if the existing row is locked; a locked fact contradicted by new extraction creates a continuity_flag of type canon_contradiction instead. canon_facts, continuity_flags
Persistence via persist_extras.py, persist_canon.py, and persist_deltas.py: Passes 9–13 are extracted by ChapterExtractor like all other passes, but their results are written to the DB by dedicated helpers: persist_scenes(), persist_knows_edges(), persist_commitments(), and persist_multi_summaries() in persist_extras.py, and persist_canon_facts() in persist_canon.py. These handle the extra logic needed for those tables (embedding, entity linking, deduplication). persist_canon_facts() upserts on (novel_id, subject_entity_id, predicate): if the existing row is locked, the incoming value is not overwritten — instead a continuity_flag of type canon_contradiction is raised. Pass 3 (state_deltas) is likewise persisted by a dedicated helper, persist_state_deltas() in persist_deltas.py, run inside the same transaction right after persist_canon_facts().
Custom entities in pass 2: When a novel has user-defined entity types (e.g., realm, power_system for LitRPG), the new_entities pass prompt is extended with those types and their descriptions. Extracted custom entities land in the custom_entities array in the extraction result and are persisted as entities rows with entity_type = <type_name>.

Mock Mode

Set USE_MOCK_LLM=true (or use --mock CLI flag) to run without an API key. The mock extractor uses regex + sentence splitting instead of LLM calls. Embeddings fall back to a deterministic SHA-256 hash. Good for local testing and CI.

Entity Resolution

Entity resolution is the process of mapping an extracted name ("Jane", "Miss Bennet", "Jane B.") to a stable UUID in the database. This prevents duplicate entity rows for the same person.

The resolver (resolver.py) uses a 5-step cascade:

flowchart TD A["Extracted name\ne.g. 'Jane B'"] --> B{Exact match\nin DB?} B -->|yes| Z[Return UUID] B -->|no| C{Alias match\nin aliases[] array?} C -->|yes| Z C -->|no| D{Partial match?\ne.g. 'Jane' matches\n'Jane Bennet'} D -->|yes| E["Add shorter form as alias\nReturn existing UUID"] D -->|no| F{Fuzzy match\n≥85% similarity?} F -->|yes| Z F -->|no| G["create=True? Create new entity, return new UUID\ncreate=False? Return None (drop reference)"] style Z fill:#1f6feb,stroke:#58a6ff,color:#e6edf3 style G fill:#3d2b1f,stroke:#f0883e,color:#e6edf3
Two dedup passes run first — before entity resolution, the IntraExtractionDeduplicator groups name variants within the extraction (rule: longest form wins, e.g., "Jane Bennet" beats "Jane"; only names actually present in the extraction may participate), then the EntityCanonicalizer merges still-unknown names into existing DB entities (deterministic normalized-equality first, LLM second) — strong-evidence merges write a permanent alias, reasoning-only merges are applied as renames to the current extraction. The resolver therefore sees cleaner input and finds canonicalized names via the renamed extraction or its alias lookup. resolve_any_entity additionally checks every typed table's name and aliases before falling back to creating a character, so an aliased faction/location/object reference can no longer create a phantom character row.
Only new_entities mints characters — the "Create new entity" leaf above fires only when the caller passes create=True, which just the authoritative new_entities pass does. Every reference-only pass — event involved_characters, scene pov/present_character_names, state_deltas, knowledge learnings, relationship/dynamics/commitment endpoints (resolve_any_entity), and canon-fact subjects — calls with create=False and simply drops the reference when the name resolves to nothing. This is what keeps game-system nouns (an "Archer Class", a "Tutorial" window, a "Skills" screen) out of the characters table: the new_entities prompt already excludes them, and no downstream pass can re-introduce them by naming them as an actor. The new_entities pass runs first within the persist transaction, so a legitimately new character is created before any reference pass needs it.

The resolver maintains an in-memory cache per pipeline run — so the second time "Jane Bennet" appears in the same chapter, it skips the DB lookup.

Relationship dedupe & repair

Persisting a relationship first checks for an existing active edge with the same unordered entity pair and rel_type (superseded_by_id IS NULL) and skips the insert when found — so "Jake–Sara: rival" re-extracted in ten chapters stays one edge. Different rel_types between the same pair coexist by design.

Repair: entity merge. When dedup gets it wrong, merge_entities (pipeline/db/entity_merge.py) merges a duplicate entity into its canonical twin in one transaction: every reference is repointed (relationships, dynamics, canon facts, commitments, events arrays, states, scenes, knowledge and possession edges), the source's name and aliases become aliases of the target (so old references keep resolving), and the source rows are deleted. Exposed as POST /api/novels/{id}/entities/merge — no longer a CLI command.

Chapter Cap (Spoiler Mode)

Every query in queries.py accepts an optional cap: int | None parameter. When set, it filters results to "as of chapter N" — you only see characters, events, and facts that existed up to that chapter number. 

# Example from queries.py
def list_characters(conn, novel_id, cap=None):
    where = "WHERE c.novel_id = %s"
    if cap is not None:
        where += " AND c.first_appearance_chapter <= %s"
    ...

The frontend chapter cap slider lives in Sidebar.tsx. It writes the cap value to the URL as a query param (?cap=5). Every page reads this param via useChapterCap() hook and passes it to the API call.

No state snapshots needed. Because every table row has a chapter reference, the DB doesn't store separate "snapshots" per chapter. The chapter cap is a pure query-time filter. This is why the schema has columns like first_appearance_chapter, opened_chapter, since_chapter, foreshadow_chapter, etc.

Database Design

The schema is at backend/pipeline/db/schema.sql — that file is the authoritative source of truth. init_db() in pipeline.py executes it on startup (it replaces the __EMBEDDING_DIM__ placeholder with the configured dimension first).

Design Principles

UUIDs everywhere

All primary keys are UUIDs generated by pgcrypto's gen_random_uuid(). No auto-increment integers.

Polymorphic entities

All characters, locations, factions, objects, and custom-typed entities share the entities table for cross-entity relationships. Entity-type tables are subsets.

Array columns for involvement

Events store involved_characters[], involved_locations[], etc. as UUID arrays instead of junction tables. Faster to write; GIN-indexed for queries.

Pgvector + HNSW

Chapters, events, scenes, commitments, and characters store vector embeddings. HNSW indexes (replacing the old IVFFlat) enable fast ANN search with better recall at novel scale.

Full-text search (BM25)

chapters, scenes, and events have a search_tsv tsvector column maintained by triggers. Used by the BM25Search component of the hybrid retriever.

Invalidate-don't-delete

Relationships and knows_edges have a superseded_by_id column. Old rows are kept; the latest non-superseded row is the current truth. Enables change history.

Temporal Model

All temporal data in Continuum uses chapter numbers as the time axis, not wall-clock time. There's no story calendar system built in — that's intentional.

Canon Facts

Canon facts are immutable statements about the story world — things that are established as ground truth (e.g., "Kira is the firstborn heir", "The sword is cursed"). They live in the canon_facts table.

ColumnMeaning
kindCategory: identity, world_rule, relationship, object_property, etc.
subject_entity_idThe entity this fact is about
predicateThe property or relationship (e.g., "is_heir", "has_curse")
valueThe fact value (e.g., "true", "Ironwood Throne")
confidence0.0–1.0 confidence from the extractor
lockedIf true, the ContinuityCritic treats violations as FAIL severity (hard error). If false, it's a WARN.

The ContinuityCritic (in backend/pipeline/critic/) uses locked canon facts to validate that new chapter extractions don't contradict established world rules.

Commitments (Foreshadow → Payoff)

A commitment is a story promise — something set up in one chapter that should pay off later. Think Chekhov's gun. The commitments table tracks these pairs.

StatusMeaning
pendingForeshadowed but not yet resolved
satisfiedThe payoff happened as promised
brokenThe story contradicted the setup
abandonedThe setup was dropped without resolution

The trigger_predicate column is a JSONB object describing the condition under which this commitment is considered resolved (e.g., {"character": "Kira", "action": "claims_throne"}). This is structured to allow future automated matching against events.

Theory of Mind (knows_edges)

The knows_edges table tracks who knows what — a "theory of mind" model for the story. This is important for dramatic irony: the reader might know a secret, but which characters know it? 

-- Example knows_edge row
character_id    → Asha's UUID
fact_description → "The king is not her biological father"
learned_chapter → 7
source_type     → "overheard"   -- or: told, witnessed, deduced, dialogue, assumed, inference
certainty       → 0.9
shared_with     → [Kira's UUID]  -- characters Asha told

The frontend's Knowledge page (/.../knowledge) shows three tabs: who-knows-what, character location history, and character possession history — all from the three bitemporal edge tables.

Entity Graph

The Entity Graph (/.../entity-graph) is a unified force-directed visualization of all entities and the edges between them. Unlike the simpler Relationships page (which shows only explicit relationship arcs), the Entity Graph assembles 5 kinds of edges into one view.

Edge KindSourceRendered As
relationshiprelationships tableSolid line, label = rel_type; arrowed unless symmetric
dynamicshared_dynamics tableSolid line, label = "dynamic"
eventCo-occurrence in events.involved_*Dashed line (story edge)
possessionpossesses_edges tableDashed line (story edge)
locationlocated_in_edges tableDashed line (story edge)

entity_a_id/entity_b_id order is meaningless for inherently mutual relationship types (spouse_of, sibling_of, etc.) — and even a label that usually reads as mutual (friend_of, rival_of) can be one-sided in a given story, so a label-only lookup can't fully capture it. The extractor is asked to judge each instance from the chapter text and set relationships.symmetric directly; the API resolves the displayed value via resolve_symmetric() in backend/api/relationship_types.py, which trusts that judgment when present and otherwise falls back to a static label allowlist (is_symmetric()). Graph views drop the arrowhead when the resolved value is true, rather than implying a direction the data doesn't have. See Schema: relationships for the full rubric.

Story edges (event, possession, location) are rendered as dashed lines with tooltips showing the underlying details. When multiple story edges exist between the same pair of entities, they are merged into a single edge — the _STORY_KIND_PRECEDENCE list in queries.py determines which edge_kind wins (possession > location > event).

The backend returns an EntityGraph response with nodes: EntityGraphNode[] and edges: GraphEdge[]. Each GraphEdge has the fields: id, from, to, label, chapter_number, edge_kind, and tooltip.

Deduplication in the query: Event co-occurrence edges are collected per unique (entity_a, entity_b) pair across all events. The query deduplicates these before merging with the other story-edge types.

How It Works End-to-End

  1. Define types at novel creation — NovelCreate.custom_entity_types accepts a list of {name, description} objects. These are written to novel_entity_types.
  2. Injected into extraction — load_story_context() fetches the types. The new_entities pass prompt is extended with the type names and descriptions.
  3. LLM extracts instances — Extracted custom entities land in the custom_entities[] array in the extraction result.
  4. Persisted as generic entities — Custom instances are written to the entities table with entity_type = <type_name>.
  5. Queryable via API — entity_types.py exposes list and detail views. The sidebar dynamically adds a nav link per custom type.

backend/pipeline/retrieval/ implements a 4-stage retrieval pipeline designed to find relevant story context from the DB for LLM-facing features (the Planner, and an eventual Drafter).

Continuity Critic

backend/pipeline/critic/ provides ContinuityCritic, which validates a DraftChapter (extracted facts before persistence) against existing DB state. It runs 6 typed checks in sequence and returns a CritiqueReport.

CheckFileWhat It Validates
Entity mentionsentity_mention_check.pyDraft mentions don't contradict canon_facts for an entity (e.g. eye colour, role); locked-fact contradiction → FAIL, unlocked → WARN
Location & possessionlocation_possession_check.pyCharacter location/possession claims don't contradict active bitemporal edges
Knowledge stateknowledge_state_check.pyKnows-edges don't contradict existing theory-of-mind state. Claims the draft marks as learned this chapter (learned_this_chapter, an explicit boolean from the claims extractor) are exempt; the rest are matched against knows_edges by word overlap, since the stored and claimed phrasings come from independent LLM calls
Temporal consistencytemporal_check.pyEvent ordering respects temporal_constraints
Commitmentscommitment_check.pyPending commitments are either advanced or acknowledged
Thread coveragethread_coverage_check.pyOpen plot threads from prior chapters receive some mention

Each finding has a severity (FAIL or WARN). The report's passed flag is False if any FAIL finding was produced. Locked canon facts that are contradicted → FAIL; unlocked → WARN.

Scene Planner

backend/pipeline/planner/ provides ScenePlanner, which generates a ChapterPlan for the next chapter given the current story state. This is an author-assist tool, not part of the ingestion pipeline.

gather_plan_context() assembles a PlanContext from the DB: main characters, active threads, pending commitments, locked canon facts, recent chapter summaries, and recent events (selected by recency, not by the Hybrid Retriever). The planner then calls LiteLLM with this context to produce a ChapterPlan — a list of ScenePlan objects (POV, location, goals, characters present, narrative beats).

Mock mode (USE_MOCK_LLM=true) emits a deterministic 2-scene plan from context without network calls, so tests run offline.

Generation Loop

backend/pipeline/generation/ closes the recursive loop: Continuum can now plan → retrieve → draft → critique → revise → ingest its own chapters. Entry point: generate_chapter(novel_id, n) in loop.py, exposed as the generate-chapter CLI subcommand, the POST /api/novels/{id}/chapters/generate job endpoint, and the "Generate chapter" mode on the Process page.

  1. Plan — ScenePlanner produces the ChapterPlan (forced to the deterministic mock plan when mocking, so --mock-llm never hits the network; in real mode planner failures raise rather than silently substituting the mock plan). The loop rejects a plan with no scenes, and resolves the plan's thread titles and commitment foreshadow texts to row uuids (read-only; unresolvable ones are dropped with a warning) before they reach the critic's SQL.
  2. Retrieve — per scene, the HybridRetriever pulls the top chapters/scenes/events matching the scene goal + cast (capped at chapter N−1, no spoilers). Computed once per scene and reused across revision iterations, since the plan is immutable; a scene whose retrieval failed is retried on the next revision.
  3. Draft — SceneDrafter writes prose per scene with the retrieved context, the plan's key facts, the prior text tail, and the novel's voice (averaged style_fingerprint of the last 3 chapters).
  4. Critique — extract_draft_claims pulls checkable claims from the draft, build_draft_chapter resolves names to ids read-only (critiquing never creates entities), and the ContinuityCritic runs its six typed checks.
  5. Revise — blocking findings become revision notes injected into a redraft, up to GENERATION_MAX_REVISIONS times.
  6. Ingest — only a passing draft is ingested, via the normal process_chapter path with source='generated'. A failing draft is returned for human review, never ingested.

State Materializer

backend/pipeline/state/ provides StateMaterializer, which derives state projections from the typed state_deltas log rather than from LLM extraction directly. It is the sole writer of character_states, and also owns located_in_edges and possesses_edges — purely deterministic and idempotent given the same delta log.

StateReplay (replay.py) reads state_deltas for a novel up to a given chapter — ordered chapter.number ASC, delta.ordinal ASC, delta.id ASC — and folds them into StateSnapshot, LocationFact, and PossessionFact objects: location deltas move the active location edge (chaining until_chapter/superseded_by_id on a move) and set the snapshot's location_id; possession deltas open/close a possesses_edges fact on gain/loss; knowledge deltas append to the snapshot's knowledge list; status deltas set one of emotional_state/goals/physical_state/appearance/notes by attribute name. There are no verb lists or event-type heuristics (the old EMOTIONAL_HINTS table is gone) — every field is set by an explicit typed delta. location/goals/knowledge/physical_state/appearance carry forward from the prior chapter's snapshot when a chapter has no delta touching that field; emotional_state intentionally does not carry forward — it reflects only what was explicitly stated for that chapter. StateMaterializer then persists the result in a single transaction. Every write is novel-scoped rebuild, not incremental upsert: each run deletes the novel's entire character_states, located_in_edges, and possesses_edges projection and re-derives it from state_deltas, so re-running is idempotent and snapshots/edges whose source deltas have since been removed or edited (e.g. a chapter re-processed with replace=true) disappear instead of surviving as stale rows.

Each run is logged to materialized_state_runs for auditability.

Invocation. process_chapter runs the materializer automatically after the chapter's persistence transaction commits, replaying through the novel's latest chapter (not just the one processed) so re-processing an earlier chapter with replace=true also rebuilds later projections. The standalone CLI (python -m pipeline.state.cli) remains available for manual backfills.
