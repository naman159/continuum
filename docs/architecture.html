Continuum

A novel continuity engine that reads raw chapter text, extracts structured knowledge via LLM, and stores it in PostgreSQL so authors and readers can query anything — "where was Asha in chapter 3?", "what commitments are still unresolved?", "who knows the secret?". The result is a living wiki that grows chapter by chapter.

Ingest

Raw chapter text → chunked, sent to LLM with story context

Extract

12-pass LLM extraction of entities, events, threads, flags, scenes, dynamics, knowledge, commitments

Query

20 wiki-style views served by FastAPI, rendered in React

Active branch: closing-the-gap-with-sota — This PR adds SOTA narrative-tracking tables (scenes, commitments, canon_facts, knows_edges, bitemporal location/possession edges). Many files in the git diff are part of this work.

Mental Model

Think of Continuum as a ETL pipeline for fiction. It does for novels what a data warehouse does for business events — continuously ingests raw narrative text and produces a structured, queryable knowledge graph.

The Pipeline (Write Path)

Chapter text → LLM extracts facts → deduplication → entity resolution → PostgreSQL. Everything flows in one direction. Nothing is updated retroactively.

The API (Read Path)

React frontend asks FastAPI for wiki views. All queries are "as-of chapter N" (the chapter cap), so you can time-travel without storing snapshots.

Three Layers of Abstraction

LayerWhat lives hereKey constraint
Entities Characters, locations, factions, objects — the nouns of the story Every entity gets a UUID in the entities table first
Events Timestamped story events — the verbs Always tied to a chapter; can reference any entity type via UUID arrays
State Character state snapshots, scenes, relationships, knowledge edges Every state row has a chapter reference → enables chapter-cap filtering
Key insight: There are no "current state" columns anywhere. State is always derived by querying up to a chapter cap. This is the design that enables spoiler-free browsing.

Pipeline Overview

The pipeline lives in backend/pipeline/pipeline.py. The entry point for processing a chapter is process_chapter(). Here's the full flow:

  1. Ingest raw text — ingest_chapter() inserts the raw chapter text into the chapters table. Duplicate (novel_id, chapter_number) is rejected.
  2. Load story context — load_story_context() fetches existing characters, locations, open plot threads, and recent events from the DB. This context is injected into every LLM prompt so the model knows what already exists.
  3. Chunk the text — sliding_window_chunks() splits the chapter into 2,000-token windows with 200-token overlap using tiktoken (falls back to whitespace split). Each chunk is processed independently.
  4. LLM extraction (12 passes per chunk) — ChapterExtractor runs 12 sequential LLM calls per chunk. See Extraction Passes for details.
  5. Merge across chunks — merge_extractions() deduplicates the results from all chunks by name/description (naïve string matching at this stage).
  6. Intra-extraction deduplication — IntraExtractionDeduplicator calls the LLM once more to group name variants ("Jane", "Jane B", "Miss Bennet") and renames all to the longest canonical form.
  7. Entity resolution — EntityResolver maps every entity name to an existing DB entity (via exact match → alias → fuzzy → create new). Returns UUIDs.
  8. Persist to DB — _persist_extraction() writes everything: entities, character states, events, relationships, shared dynamics, plot threads, continuity flags.
  9. Embed — embed_chapter_and_events() generates vector embeddings for the chapter summary and each event description (enables semantic search later).
  10. Persist SOTA extras — persist_multi_summaries(), persist_scenes(), persist_knows_edges(), persist_commitments() fill the newer tables added in the SOTA branch.
Note on idempotency: Processing the same chapter twice is not safe — ingest rejects duplicate chapter numbers, but the later persistence steps don't check for duplicates. Don't call process_chapter() twice on the same chapter.

12 Extraction Passes

Each pass is a separate LLM call. The schema for what each pass returns is in prompts.py → PASS_SCHEMAS. The order matters — later passes can reference entities found in earlier ones via the merged context.

# Pass Name What It Extracts DB Target
1 chapter_summary One-sentence chapter summary chapters.summary
2 new_entities New characters, locations (with parent_location), factions, objects (with owner_name + distinguishing_properties) characters, locations, factions, objects
3 entity_deltas Character state changes: location, emotional state, goals, knowledge character_states
4 events Narrative events with type, impact level, involved entities events
5 thread_updates Plot thread open/progress/close with linked events plot_threads, thread_events
6 continuity_flags Foreshadowing, setups, callbacks, planted details continuity_flags
7 relationship_updates Entity-to-entity relationship arcs with type, direction, chapter range relationships
8 dynamics_updates Chapter-level snapshots of how two entities interact (tone, tension) shared_dynamics
9 scene_segmentation Scene boundaries with POV character, location, time anchor, present characters scenes
10 multi_granularity_summaries Summary at three granularities: short (tweet), medium (paragraph), long (recap) chapters.summary_short, summary_medium, summary_long
11 knowledge_state_deltas Who learns what, certainty, how it was learned, who it was shared with knows_edges
12 commitments Foreshadow → payoff pairs (Chekhov's guns), trigger predicates, weight commitments
Persistence via persist_extras.py: Passes 9–12 are extracted by ChapterExtractor like all other passes, but their results are written to the DB by dedicated helpers in persist_extras.py (persist_scenes(), persist_knows_edges(), persist_commitments(), persist_multi_summaries()), which handle the extra logic needed for those tables (embedding, entity linking, deduplication).

Mock Mode

Set USE_MOCK_LLM=true (or use --mock CLI flag) to run without an API key. The mock extractor uses regex + sentence splitting instead of LLM calls. Embeddings fall back to a deterministic SHA-256 hash. Good for local testing and CI.

Entity Resolution

Entity resolution is the process of mapping an extracted name ("Jane", "Miss Bennet", "Jane B.") to a stable UUID in the database. This prevents duplicate entity rows for the same person.

The resolver (resolver.py) uses a 5-step cascade:

flowchart TD A["Extracted name\ne.g. 'Jane B'"] --> B{Exact match\nin DB?} B -->|yes| Z[Return UUID] B -->|no| C{Alias match\nin aliases[] array?} C -->|yes| Z C -->|no| D{Partial match?\ne.g. 'Jane' matches\n'Jane Bennet'} D -->|yes| E["Add shorter form as alias\nReturn existing UUID"] D -->|no| F{Fuzzy match\n≥85% similarity?} F -->|yes| Z F -->|no| G["Create new entity\nReturn new UUID"] style Z fill:#1f6feb,stroke:#58a6ff,color:#e6edf3 style G fill:#3d2b1f,stroke:#f0883e,color:#e6edf3
Intra-extraction dedup runs first — before entity resolution, the IntraExtractionDeduplicator uses an LLM call to group all name variants within a single extraction and renames them to the longest canonical form. This means the resolver sees cleaner input. The deduplicator uses the rule: longest form wins (e.g., "Jane Bennet" beats "Jane").

The resolver maintains an in-memory cache per pipeline run — so the second time "Jane Bennet" appears in the same chapter, it skips the DB lookup.

Chapter Cap (Spoiler Mode)

Every query in queries.py accepts an optional cap: int | None parameter. When set, it filters results to "as of chapter N" — you only see characters, events, and facts that existed up to that chapter number. 

# Example from queries.py
def list_characters(conn, novel_id, cap=None):
    where = "WHERE c.novel_id = %s"
    if cap is not None:
        where += " AND c.first_appearance_chapter <= %s"
    ...

The frontend chapter cap slider lives in Sidebar.tsx. It writes the cap value to the URL as a query param (?cap=5). Every page reads this param via useChapterCap() hook and passes it to the API call.

No state snapshots needed. Because every table row has a chapter reference, the DB doesn't store separate "snapshots" per chapter. The chapter cap is a pure query-time filter. This is why the schema has columns like first_appearance_chapter, opened_chapter, since_chapter, foreshadow_chapter, etc.

Database Design

The schema is at backend/pipeline/db/schema.sql — that file is the authoritative source of truth. init_db() in pipeline.py executes it on startup (it replaces the __EMBEDDING_DIM__ placeholder with the configured dimension first).

Design Principles

UUIDs everywhere

All primary keys are UUIDs generated by pgcrypto's gen_random_uuid(). No auto-increment integers.

Polymorphic entities

All characters, locations, factions, and objects share the entities table for cross-entity relationships. Entity-type tables are subsets.

Array columns for involvement

Events store involved_characters[], involved_locations[], etc. as UUID arrays instead of junction tables. Faster to write; GIN-indexed for queries.

Pgvector embeddings

Chapters, events, scenes, commitments, and characters store vector embeddings. HNSW indexes enable fast ANN (approximate nearest neighbor) search.

Core Tables

These tables exist from the beginning of the project and support the 6 base extraction passes.

SOTA Tables New in this branch

These tables were added on the closing-the-gap-with-sota branch to bring the extraction quality closer to state-of-the-art narrative understanding systems.

TableWhat It TracksKey Columns
scenes Individual scenes within a chapter: who's present, where, when, what POV chapter_id, scene_index, pov_character_id, location_id, time_anchor, present_characters[], summary, embedding
canon_facts Immutable facts about the world. Can be "locked" so violations are hard errors. novel_id, kind, subject_entity_id, predicate, value, source_chapter, confidence, locked
knows_edges "Theory of mind" — who knows what fact, when they learned it, how certain they are character_id, fact_description, learned_chapter, source_event_id, source_type, certainty, shared_with[]
possesses_edges Bitemporal object possession: character owns object from chapter X to Y character_id, object_id, since_chapter, until_chapter, evidence_event_id, certainty
located_in_edges Bitemporal entity location: entity was at location from chapter X to Y entity_id, location_id, since_chapter, until_chapter, evidence_event_id, certainty
commitments Foreshadow/payoff pairs: a story promise and its resolution (or lack thereof) foreshadow_text, foreshadow_chapter, trigger_predicate (JSONB), payoff_text, payoff_chapter, status, weight
temporal_constraints Ordering constraints between events (A before B, A causes B) event_a_id, event_b_id, relation, certainty
Bitemporal edges (since_chapter, until_chapter) allow tracking "Asha had the sword from chapter 2 to chapter 7, then Kira had it from chapter 7 onward" — without storing multiple snapshots. A NULL until_chapter means "still true."

Temporal Model

All temporal data in Continuum uses chapter numbers as the time axis, not wall-clock time. There's no story calendar system built in — that's intentional.

How Chapter Cap Works on Each Table Type

Table TypeCap Filter PatternExample
Point-in-time WHERE chapter_number <= cap events, character_states
First appearance WHERE first_appearance_chapter <= cap characters, objects, locations
Opened/closed arcs WHERE opened_chapter <= cap plot_threads
Bitemporal edges WHERE since_chapter <= cap located_in_edges, possesses_edges
Commitments WHERE foreshadow_chapter <= cap commitments

Canon Facts

Canon facts are immutable statements about the story world — things that are established as ground truth (e.g., "Kira is the firstborn heir", "The sword is cursed"). They live in the canon_facts table.

ColumnMeaning
kindCategory: identity, world_rule, relationship, object_property, etc.
subject_entity_idThe entity this fact is about
predicateThe property or relationship (e.g., "is_heir", "has_curse")
valueThe fact value (e.g., "true", "Ironwood Throne")
confidence0.0–1.0 confidence from the extractor
lockedIf true, future chapters violating this fact trigger a hard error (critic mode). If false, it's a warning.

The critic system (planned in backend/pipeline/critic/) uses canon facts to validate that new chapter extractions don't contradict established world rules.

Commitments (Foreshadow → Payoff)

A commitment is a story promise — something set up in one chapter that should pay off later. Think Chekhov's gun. The commitments table tracks these pairs.

StatusMeaning
pendingForeshadowed but not yet resolved
satisfiedThe payoff happened as promised
brokenThe story contradicted the setup
abandonedThe setup was dropped without resolution

The trigger_predicate column is a JSONB object describing the condition under which this commitment is considered resolved (e.g., {"character": "Kira", "action": "claims_throne"}). This is structured to allow future automated matching against events.

Theory of Mind (knows_edges)

The knows_edges table tracks who knows what — a "theory of mind" model for the story. This is important for dramatic irony: the reader might know a secret, but which characters know it? 

-- Example knows_edge row
character_id    → Asha's UUID
fact_description → "The king is not her biological father"
learned_chapter → 7
source_type     → "overheard"   -- or: told, witnessed, deduced, read
certainty       → 0.9
shared_with     → [Kira's UUID]  -- characters Asha told

The frontend's Knowledge page (/.../knowledge) shows three tabs: who-knows-what, character location history, and character possession history — all from the three bitemporal edge tables.
