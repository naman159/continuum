Continuum

A novel continuity engine that reads raw chapter text, extracts structured knowledge via LLM, and stores it in PostgreSQL so authors and readers can query anything — "where was Asha in chapter 3?", "what commitments are still unresolved?", "who knows the secret?". The result is a living wiki that grows chapter by chapter.

Ingest

Raw chapter text → chunked, sent to LLM with story context

Extract

13-pass LLM extraction of entities, events, threads, flags, scenes, dynamics, knowledge, commitments, canon facts

Query

25+ wiki-style views served by FastAPI, rendered in React — including entity graph, scenes, canon facts, and custom entity types

Status: redesign complete (2026-07-13/14); write refusal added 2026-08-24, unified into a single caller-agnostic critique 2026-09-04. Continuum is a continuity analyzer, not a chapter generator — that product decision is final, not provisional. Two spines run over one Postgres database: the write spine (analyze_chapter) turns raw chapter text — from the Process page/CLI (source='human') or an MCP save_chapter call from a writing agent (source='agent') — into structured knowledge, and the read layer (backend/reads/) serves every wiki page, API route, and MCP tool from that same data, cutoff-aware by construction. The write spine does not branch on who is writing: every caller runs CRITIQUE → INGEST → EXTRACT → PERSIST → MATERIALIZE → RECORD, with the critique run once, up front. Only the consequence of a FAIL varies, via the caller's on_continuity_fail policy — see Pipeline Overview and Blocking vs Advisory below. See State of the System for the full history of how it got here.

Mental Model

Think of Continuum as a ETL pipeline for fiction. It does for novels what a data warehouse does for business events — continuously ingests raw narrative text and produces a structured, queryable knowledge graph.

The Pipeline (Write Path)

Chapter text → LLM extracts facts → deduplication → entity resolution → PostgreSQL. Everything flows in one direction. Nothing is updated retroactively.

The API (Read Path)

React frontend asks FastAPI for wiki views. All queries are "as-of chapter N" (the chapter cap), so you can time-travel without storing snapshots.

Three Layers of Abstraction

LayerWhat lives hereKey constraint
Entities Characters, locations, factions, objects, and user-defined custom types — the nouns of the story Every entity gets a UUID in the entities table first
Events Timestamped story events — the verbs. Now enriched with SVO triples and story-time ordering. Always tied to a chapter; can reference any entity type via UUID arrays
State Character state snapshots, scenes, relationships, knowledge edges, bitemporal possession/location edges Every state row has a chapter reference → enables chapter-cap filtering
Key insight: There are no "current state" columns anywhere. State is always derived by querying up to a chapter cap. This is the design that enables spoiler-free browsing.

Pipeline Overview

The pipeline lives in backend/pipeline/pipeline.py. The entry point for processing a chapter is analyze_chapter(). Here's the full flow:

  1. 0 · CRITIQUE — every caller, exactly once — runs before anything else. critique_draft() (pipeline/critic/service.py) runs extract_draft_claims() (one LLM call) → build_draft_chapter() → ContinuityCritic.critique() against the raw, unextracted text. It returns a DraftCritique and never raises: status="ok" carries a real verdict, "error" means the critique itself blew up, and "unavailable" means it never ran (CRITIC_ENABLED=false, or no real model — an empty mock draft would pass every check vacuously, so mock mode is an outage rather than a pass). This is the only critique the chapter gets; phase 5 persists this report rather than computing a second one. Running before chunking and the 13-pass extractor is what makes a refusal cost one LLM call instead of thirteen — and, more importantly, what keeps refused text out of the write tier entirely, since delete_chapter_data cannot undo the entity rows, plot_threads upserts and canon_facts updates a rejected draft would leave behind. What a FAIL costs is the caller's on_continuity_fail policy, not this function's business — see Blocking vs Advisory below.
  2. Ingest raw text — ingest_chapter() inserts the raw chapter text into the chapters table. Duplicate (novel_id, chapter_number) is rejected.
  3. Load story context — load_story_context() fetches existing characters, locations, open plot threads, recent events, and custom entity types from the DB. Characters and locations are selected, not dumped: entities whose name or alias appears in the chapter text always make the cut, the remainder back-fills by recency, and the lists are capped at CONTEXT_MAX_CHARACTERS (default 40) / CONTEXT_MAX_LOCATIONS (default 30) so prompt size stays bounded as the cast grows. The result is injected into every LLM prompt so the model knows what already exists.
  4. Chunk the text — sliding_window_chunks() splits the chapter into 2,000-token windows with 200-token overlap using tiktoken. The encoding is derived from DEFAULT_MODEL (o200k_base for GPT-4o-class models, and as the estimator for any model tiktoken cannot map — every Gemini and Claude model). There is no whitespace fallback: a silently coarser window changes both chunk size and paragraph structure with nothing to detect it afterward, so a tokenizer that will not load raises. Each chunk is processed independently.
  5. LLM extraction (13 passes per chunk) — ChapterExtractor runs 13 sequential LLM calls per chunk. See Extraction Passes for details.
  6. Merge across chunks — merge_extractions() deduplicates the results from all chunks by name/description (naïve string matching at this stage; objects are keyed by name + owner so same-named items with different owners survive the merge).
  7. Intra-extraction deduplication — IntraExtractionDeduplicator makes one focused LLM call per entity type (including the novel's custom types) to group name variants ("Jane", "Jane B", "Miss Bennet") and renames every occurrence to the longest canonical form — across new entities, deltas, events (characters, locations, objects, and factions), relationships, dynamics, scenes, learnings, and custom entities. Group members are validated against the actually-extracted names, so an LLM-hallucinated name can never become the canonical form. Renamed lists are also de-duplicated in place.
  8. Cross-chapter canonicalization — EntityCanonicalizer matches names not yet in the DB against the per-type roster. Names whose normalized form (normalize_name(): case, whitespace, surrounding punctuation, leading article) equals exactly one roster name/alias merge deterministically with zero LLM cost; only the rest go to one LLM call per type, with the roster capped to the CANONICALIZER_MAX_ROSTER (default 80) most string-similar entries so prompt size stays bounded as the novel grows. Matches confirmed by strong evidence (a verbatim anchor, or unambiguous lexical closeness for non-characters) are appended to the entity's aliases[] — custom entity types store theirs on entities.aliases; reasoning-only matches are instead applied as a rename to the current extraction (no permanent alias), so the merge still takes effect this chapter.
  9. Entity resolution — EntityResolver maps every entity name to an existing DB entity (exact name → alias → character partial-name match → create new). Returns UUIDs. Only the new_entities pass is allowed to create characters; every other pass resolves with create=False (resolve-or-skip) so a name it merely references can't mint a phantom character.
  10. Persist to DB — _persist_extraction() writes entities, events, relationships, shared dynamics, plot threads, continuity flags. It never writes character_states: state changes go through the typed state_deltas log instead, and character_states is the sole responsibility of the State Materializer, which runs at the end of analyze_chapter.
  11. Persist state deltas — persist_state_deltas() (persist_deltas.py) writes the state_deltas extraction pass into the state_deltas table: reference-only resolution (create=False) for the subject character, and for possession/location kinds the object/location too, so a delta naming an unknown entity is dropped rather than minting one. Rows carry subject_id/object_id as universal entities.id and location_id as the typed locations.id, with an ordinal preserving narrative order within the chapter — this is the tier-2 log the state materializer replays.
  12. Embed — embed_chapter_and_events() generates vector embeddings for each event description, plus the chapter summary only when no medium summary exists (otherwise persist_multi_summaries() embeds the chapter from summary_medium, so the extra call is skipped).
  13. Persist SOTA extras — persist_multi_summaries(), persist_scenes(), persist_knows_edges(), persist_commitments(), persist_canon_facts() fill the newer tables added in the SOTA branch. Canon facts upsert unless locked — a locked fact contradicted by extraction becomes a continuity_flag (flag_type='canon_contradiction') rather than an overwrite. The per-row "log and continue" blocks in persist_extras.py each run inside a SAVEPOINT (_row_savepoint()) — see the callout below for why that is load-bearing.
  14. 4 · MATERIALIZE — runs outside the persistence transaction, after it commits: StateMaterializer replays state_deltas through the novel's latest chapter. A failure here is caught and logged, not raised — the already-committed chapter stays saved, and the result dict's "materialized" flag tells the caller a manual re-run (python -m pipeline.state.cli) is needed.
  15. 5 · RECORD — persist the phase-0 verdict — no second judgement. persist_critique() (pipeline/critic/persist.py) writes the report phase 0 already produced to critique_reports/critique_findings, replacing any prior report for the chapter. The only reason this is a separate phase is that critique_reports.chapter_id is a foreign key: the chapter has to exist before its verdict can be filed against it. Skipped when phase 0 was skipped (CRITIC_ENABLED=false or run_critic: false) or produced no report (an outage) — a missing verdict must not overwrite an existing one with an empty one. Like phase 4 this is derived and idempotent: a failure is caught and logged rather than raised, and python -m pipeline.critic.cli --novel-id <uuid> [--chapter N] re-judges one chapter or a whole back catalogue from stored text without re-extracting — the recovery path after a transient failure or a change to a check. Because the checks compare this chapter's claims against the world state entering it, judging pre-ingest is not just cheaper but semantically cleaner: the chapter's own canon facts are not yet committed, so a mention cannot be compared against the row it just produced. (The entity-mention check still bounds itself to source_chapter < chapter_number, which is what makes a standalone re-run correct too.)
Blocking vs advisory (write refusal added 2026-08-24; unified 2026-09-04). Originally this was a separate "agent write gate": a second module that critiqued the draft, decided, and refused — while phase 5 critiqued the same prose a second time to produce the report. Two invocations, two LLM calls, one set of checks. They are now one phase. The judgement is caller-agnostic and runs once; only the consequence of a FAIL is a policy.
  • on_continuity_fail="warn" — the default. Record the findings and ingest anyway. Used by the Process page and the CLI, where a human is already the review step: telling them to approve their own draft would be ceremony, not safety. The report lands in critique_reports and surfaces in the Continuity view.
  • on_continuity_fail="block". Refuse the write, park the draft, return {"ingested": false, "status", "submission_id", "reason", "fails", "warns"} — no exception, no chapters row. Asked for by exactly one caller: mcp_server/queries.py::save_chapter, because an agent writes to canon unattended and at volume. Being the MCP tool is what makes a caller an agent; it is not a string any caller can pass, which is the failure mode the old source != 'human' test had.
The invariant is a property of the policy, not of the row. A chapter written through save_chapter either passed continuity or was human-overridden through the Review queue with the blocking findings recorded on it. Rows from warning callers carry their findings without that guarantee. The refused text is never lost — it lands in draft_submissions, a table that is deliberately not canon and is never read by any query serving the wiki, the API, or MCP tools other than the review queue itself.
  • Fail-closed, not fail-open. A blocking caller refuses on every outcome that is not a clean pass. If the critique throws — bad prompt, malformed CritiqueReport, anything — critique_draft() catches it and returns status="error"; the draft is parked (reason: "error", status: "pending_review"). If it never ran at all (status="unavailable": CRITIC_ENABLED=false, or mock mode) the write is refused with nothing parked — there is no verdict for a human to adjudicate, so status is "refused" and submission_id is null. The caller holds the text and retries. A missing verdict is never a pass, and run_critic=false cannot disable the check a blocking caller depends on.
  • Resubmission always clears the stale row. A pending row for a chapter is superseded (marked rejected) the moment a new draft is judged for that same chapter — whether the new draft fails again or passes cleanly. A passing resubmission does not insert a row of its own; it only clears the one left by the earlier failure. Without this, a chapter that failed once and then passed would leave a stale pending row in the queue forever, pointing at superseded text a reviewer can no longer accept (the chapter it names already exists).
  • The human is the only override. A parked draft sits in the wiki's Review Queue (/novels/{id}/review, routes/Review.tsx) until a human accepts or rejects it. Rejecting just marks the row; the agent must revise and resubmit. Accepting re-runs analyze_chapter under on_continuity_fail="warn" — the reviewer is the review step — and, critically, does not discard the findings that blocked the draft: they are written through to continuity_flags as accepted_override:<check> rows, so a human-blessed contradiction stays visible in the Continuity view instead of being silently absolved. If the human edited the text before accepting, the flag is labelled [accepted after edit; original draft FAILed] rather than [accepted despite continuity FAIL] — the re-ingest critiques the edited text into critique_reports, but never re-adjudicates the blocking verdict, so the flag records only that the original draft failed.
  • Human writes are advisory, not unchecked. The Process page and the CLI run the identical five checks on the identical claims and get the identical findings; they simply do not treat a FAIL as a veto. This is the part the old design got wrong by omission: because the gate was a separate module reachable only via source != 'human', "human" was a string any caller could pass to skip the check entirely. Now source is provenance only — it lands in chapters.source and decides nothing.
See draft_submissions schema and the review-queue API in the Reference for the exact shapes.
Relationship reads mean "in force at the cutoff" (fixed 2026-08-17). Two defects made relationship answers wrong rather than merely incomplete. reads/characters.py required entity_type = 'character' on both endpoints, so every character↔object/location/faction edge was invisible from the character's side — GET /objects/{id} showed "Aelric wields Duskbrand" while GET /characters/{aelric} and the MCP get_character tool showed nothing, and rel_to_row's other_entity_type resolution was unreachable code. Separately, relationships.to_chapter appeared in zero WHERE clauses repo-wide, so every read meant "started before N", never "still true at N" — an alliance that broke in chapter 6 was still reported as current at chapter 20. All five relationship reads now filter to_chapter and superseded_by_id, and list_location_edges/list_possession_edges filter superseded_by_id under active_only so a character who moves twice in one chapter no longer reads as being in two places at once.
A relationship persists until the text breaks it (fixed 2026-09-04). to_chapter means the relationship stopped being true. The extraction prompt never said so — the schema offered from_chapter and to_chapter as bare integer|null fields with no definition — so the model filled to_chapter with the chapter it was reading, meaning "this is what I saw here". Every relationship was therefore stored as having ended the moment it began. Absence of a re-mention was being recorded as an ending.

The read layer then did exactly what it was told. Because relationship_graph derives its nodes from its edges, a character whose only relationships were closed-on-arrival disappeared from the graph one chapter later. On a Pride and Prejudice ingest the graph went from 10 nodes at chapter 1 to 8 at chapter 2, losing a married couple the book never separates — a cutoff that removed people as it moved forward. The prompt now defines the interval, and reads/tests/test_timeline_graphs.py pins both halves of the contract: raising the cutoff can never drop a node, and a relationship the text genuinely ends does leave the graph at its to_chapter.
Entity identity is additive-only (fixed 2026-08-17). Two resolver defects could silently and permanently corrupt identity, which for a memory layer is worse than a missing answer — a wrong merge is unrecoverable without manual repair and poisons every later chapter. The partial-name branch used LIMIT 1 with no ORDER BY, so a bare "Elizabeth" bound to whichever of Elizabeth Bennet / Elizabeth Elliot the planner happened to return, and then persisted that guess as an alias. It now returns every candidate and refuses to bind when more than one matches. Alias writes are also gated on create=True: reference-only passes (scene POV, knows-edges, event actors, state deltas) resolve for lookup and must not mutate identity. Conversely, _merge_aliases() now folds extractor-supplied aliases into entities that already exist — previously they were written only on create, so a nickname established in a later chapter was discarded and its next bare use minted a duplicate character.
Best-effort persistence requires savepoints (fixed 2026-08-16). persist_scenes(), persist_knows_edges() and persist_commitments() catch per-row failures so one bad scene doesn't cost the chapter. That intent was inverted in practice: PostgreSQL aborts the whole transaction on any statement error, and DBSession issued no savepoints, so after the first failure every later statement raised InFailedSqlTransaction — swallowed in turn by the next handler. Two outcomes followed, both losing the entire chapter. If a later unguarded step (persist_canon_facts() or persist_state_deltas(), neither of which catches) issued a statement, it raised and rolled back, reporting "current transaction is aborted" while the real cause appeared only as a lone WARNING scene insert failed. If neither had rows to write, nothing raised at all: COMMIT on an aborted transaction is silently converted to ROLLBACK by PostgreSQL, so analyze_chapter returned a success payload carrying a chapter_id for a row that no longer existed. Every one of those handlers was marked # pragma: no cover, which is why a green suite never caught it. DBSession.savepoint() now wraps each block, and pipeline/db/tests/test_session_savepoint_integration.py pins both the fix and a characterization of the old silent-discard behaviour.
Embedding failures now raise instead of substituting a hash vector. EmbeddingService.embed_text() used to catch every failure — rate limit, timeout, missing key, wrong dimensions — and return _hash_embedding(), whose SHA-256 output carries no semantic signal whatsoever: two strings differing only by a trailing period measure ≈ −0.016 cosine against each other, while two entirely unrelated texts measure ≈ −0.001. Those vectors were written to chapters, events, scenes and commitments and indexed by HNSW, permanently and undetectably degrading dense retrieval for whatever they touched. Outside explicit mock mode the service now raises EmbeddingError, and asserts the returned vector width matches EMBEDDING_DIMENSIONS before handing it back.

Those four tables also carry an embedding_model column recording what produced each vector (mock:hash for mock runs, otherwise the configured model). This is not only about the historical rows: USE_MOCK_LLM writes hash vectors legitimately, so ingesting with mock and later switching to a real model is the normal development path and produces a silently mixed store. To find rows that no longer match the current configuration: 
SELECT embedding_model, count(*) FROM chapters GROUP BY 1;
Rows with NULL predate the column; rows tagged mock:hash carry no semantic content and should be re-ingested before dense retrieval is trusted.
Note on idempotency: Re-processing a chapter requires passing replace=True (API: "replace": true in the ProcessRequest body). Without it, ingest rejects duplicate chapter numbers. With replace=True, delete_chapter_data() removes the following chapter-scoped derived rows before re-processing begins:
  • events, scenes, character_states, continuity_flags, shared_dynamics — deleted by chapter_id
  • relationships rows that carry a chapter_id (i.e. those written during this chapter's ingest)
  • knows_edges and commitments keyed by chapter number — deleted by chapter_number
Entity rows introduced by the chapter (characters, locations, factions, objects, entities) and plot-thread upserts are not deleted — they survive and are resolved against on re-processing, so entity identity remains stable across replace runs.

13 Extraction Passes

Each pass is a separate LLM call. The schema for what each pass returns is in prompts.py → PASS_SCHEMAS. The order matters — later passes can reference entities found in earlier ones via the merged context.

# Pass Name What It Extracts DB Target
1 chapter_summary One-sentence chapter summary chapters.summary
2 new_entities New characters, locations (with parent_location), factions, objects (with owner_name + distinguishing_properties), and custom entities (genre-specific types defined per novel) characters, locations, factions, objects, entities (for custom types)
3 state_deltas Typed state changes: possession gain/loss, location moves, knowledge learned, status updates (emotional_state/goals/physical_state/appearance/notes) — each with a verbatim evidence quote state_deltas (folded into character_states and the bitemporal edges by the materializer)
4 events Narrative events with type, impact level, involved entities events
5 thread_updates Plot thread open/progress/close with linked events plot_threads, thread_events
6 continuity_flags Foreshadowing, setups, callbacks, planted details continuity_flags
7 relationship_updates Entity-to-entity relationship arcs with type, direction, chapter range relationships
8 dynamics_updates Chapter-level snapshots of how two entities interact (tone, tension). Multiple updates for the same pair in one chapter (in either order) are merged into a single row — descriptions concatenated — to satisfy the one-row-per-pair-per-chapter unique constraint shared_dynamics
9 scene_segmentation Scene boundaries with POV character, location, time anchor, present characters scenes
10 multi_granularity_summaries Summary at three granularities: short (tweet), medium (paragraph), long (recap) chapters.summary_short, summary_medium, summary_long
11 knowledge_state_deltas Who learns what, certainty, how it was learned, who it was shared with knows_edges
12 commitments Foreshadow → payoff pairs (Chekhov's guns), trigger predicates, weight commitments
13 canon_facts Lockable world-facts: kind, subject entity, predicate, value, confidence. Upserts on (novel_id, subject_entity_id, predicate) — skips update if the existing row is locked; a locked fact contradicted by new extraction creates a continuity_flag of type canon_contradiction instead. canon_facts, continuity_flags
Persistence via persist_extras.py, persist_canon.py, and persist_deltas.py: Passes 9–13 are extracted by ChapterExtractor like all other passes, but their results are written to the DB by dedicated helpers: persist_scenes(), persist_knows_edges(), persist_commitments(), and persist_multi_summaries() in persist_extras.py, and persist_canon_facts() in persist_canon.py. These handle the extra logic needed for those tables (embedding, entity linking, deduplication). persist_canon_facts() upserts on (novel_id, subject_entity_id, predicate): if the existing row is locked, the incoming value is not overwritten — instead a continuity_flag of type canon_contradiction is raised. Pass 3 (state_deltas) is likewise persisted by a dedicated helper, persist_state_deltas() in persist_deltas.py, run inside the same transaction right after persist_canon_facts().
Custom entities in pass 2: When a novel has user-defined entity types (e.g., realm, power_system for LitRPG), the new_entities pass prompt is extended with those types and their descriptions. Extracted custom entities land in the custom_entities array in the extraction result and are persisted as entities rows with entity_type = <type_name>.

Entity Resolution

Entity resolution is the process of mapping an extracted name ("Jane", "Miss Bennet", "Jane B.") to a stable UUID in the database. This prevents duplicate entity rows for the same person.

The resolver (resolver.py) uses a 5-step cascade:

Two dedup passes run first — before entity resolution, the IntraExtractionDeduplicator groups name variants within the extraction (rule: longest form wins, e.g., "Jane Bennet" beats "Jane"; only names actually present in the extraction may participate), then the EntityCanonicalizer merges still-unknown names into existing DB entities (deterministic normalized-equality first, LLM second) — strong-evidence merges write a permanent alias, reasoning-only merges are applied as renames to the current extraction. The resolver therefore sees cleaner input and finds canonicalized names via the renamed extraction or its alias lookup. resolve_any_entity additionally checks every typed table's name and aliases before falling back to creating a character, so an aliased faction/location/object reference can no longer create a phantom character row.
Only new_entities mints characters — the "Create new entity" leaf above fires only when the caller passes create=True, which just the authoritative new_entities pass does. Every reference-only pass — event involved_characters, scene pov/present_character_names, state_deltas, knowledge learnings, relationship/dynamics/commitment endpoints (resolve_any_entity), and canon-fact subjects — calls with create=False and simply drops the reference when the name resolves to nothing. This is what keeps game-system nouns (an "Archer Class", a "Tutorial" window, a "Skills" screen) out of the characters table: the new_entities prompt already excludes them, and no downstream pass can re-introduce them by naming them as an actor. The new_entities pass runs first within the persist transaction, so a legitimately new character is created before any reference pass needs it.

The resolver maintains an in-memory cache per pipeline run — so the second time "Jane Bennet" appears in the same chapter, it skips the DB lookup.

Relationship dedupe & repair

Persisting a relationship first checks for an existing active edge with the same unordered entity pair and rel_type (superseded_by_id IS NULL) and skips the insert when found — so "Jake–Sara: rival" re-extracted in ten chapters stays one edge. Different rel_types between the same pair coexist by design.

Repair: entity merge. When dedup gets it wrong, merge_entities (pipeline/db/entity_merge.py) merges a duplicate entity into its canonical twin in one transaction: every reference is repointed (relationships, dynamics, canon facts, commitments, events arrays, states, scenes, knowledge and possession edges), the source's name and aliases become aliases of the target (so old references keep resolving), and the source rows are deleted. Exposed as POST /api/novels/{id}/entities/merge — no longer a CLI command.

Chapter Cap (Spoiler Mode)

Every public function in reads/ takes up_to_chapter: int | None as its third positional parameter (after db, novel_id). When set, it filters results to "as of chapter N" — you only see characters, events, and facts that existed up to that chapter number. None resolves to the novel's current max chapter via reads.common.resolve_cutoff, so no row from beyond the cutoff is ever returned. This isn't just convention: reads/tests/test_contract.py enforces it structurally — it walks every module in reads/ via pkgutil and fails the build if a public function is missing the parameter, except the handful of documented exemptions in its CUTOFF_EXEMPT set (registry reads like list_novels/get_novel, list_entity_types, and pure label-classification helpers with no db/novel_id at all). Routes and MCP tools translate their own cap/writing_chapter parameters into this contract at the boundary; the same test also asserts api/routes/*.py and mcp_server/server.py contain no SQL, so cutoff logic can't silently duplicate outside reads/. 

# Example from reads/characters.py
def list_characters(db, novel_id, up_to_chapter=None):
    cutoff = resolve_cutoff(db, novel_id, up_to_chapter)
    return db.fetchall(
        "SELECT ... FROM characters c WHERE c.novel_id = %s "
        "AND c.first_appearance_chapter <= %s",
        (novel_id, cutoff),
    )

The frontend chapter cap slider lives in Sidebar.tsx. It writes the cap value to the URL as a query param (?cap=5). Every page reads this param via useChapterCap() hook and passes it to the API call.

No state snapshots needed. Because every table row has a chapter reference, the DB doesn't store separate "snapshots" per chapter. The chapter cap is a pure query-time filter. This is why the schema has columns like first_appearance_chapter, opened_chapter, since_chapter, foreshadow_chapter, etc.

Database Design

The schema is at backend/pipeline/db/schema.sql — that file is the authoritative source of truth. init_db() in pipeline.py executes it on startup (it replaces the __EMBEDDING_DIM__ placeholder with the configured dimension first).

Design Principles

UUIDs everywhere

All primary keys are UUIDs generated by pgcrypto's gen_random_uuid(). No auto-increment integers.

Polymorphic entities

All characters, locations, factions, objects, and custom-typed entities share the entities table for cross-entity relationships. Entity-type tables are subsets.

Array columns for involvement

Events store involved_characters[], involved_locations[], etc. as UUID arrays instead of junction tables. Faster to write; GIN-indexed for queries.

Pgvector + HNSW

Chapters, events, scenes, commitments, and characters store vector embeddings. HNSW indexes (replacing the old IVFFlat) enable fast ANN search with better recall at novel scale.

Full-text search (BM25)

chapters, scenes, and events have a search_tsv tsvector column maintained by triggers. Used by the BM25Search component of the hybrid retriever.

Invalidate-don't-delete

Relationships and knows_edges have a superseded_by_id column. Old rows are kept; the latest non-superseded row is the current truth. Enables change history.

How It Works End-to-End

  1. Define types at novel creation — NovelCreate.custom_entity_types accepts a list of {name, description} objects. These are written to novel_entity_types.

State Materializer

backend/pipeline/state/ provides StateMaterializer, which derives state projections from the typed state_deltas log rather than from LLM extraction directly. It is the sole writer of character_states, and also owns located_in_edges and possesses_edges — purely deterministic and idempotent given the same delta log.

StateReplay (replay.py) reads state_deltas for a novel up to a given chapter — ordered chapter.number ASC, delta.ordinal ASC, delta.id ASC — and folds them into StateSnapshot, LocationFact, and PossessionFact objects: location deltas move the active location edge (chaining until_chapter/superseded_by_id on a move) and set the snapshot's location_id; possession deltas open/close a possesses_edges fact on gain/loss; knowledge deltas append to the snapshot's knowledge list; status deltas set one of emotional_state/goals/physical_state/appearance/notes by attribute name. There are no verb lists or event-type heuristics (the old EMOTIONAL_HINTS table is gone) — every field is set by an explicit typed delta. location/goals/knowledge/physical_state/appearance carry forward from the prior chapter's snapshot when a chapter has no delta touching that field; emotional_state intentionally does not carry forward — it reflects only what was explicitly stated for that chapter. StateMaterializer then persists the result in a single transaction. Every write is novel-scoped rebuild, not incremental upsert: each run deletes the novel's entire character_states, located_in_edges, and possesses_edges projection and re-derives it from state_deltas, so re-running is idempotent and snapshots/edges whose source deltas have since been removed or edited (e.g. a chapter re-processed with replace=true) disappear instead of surviving as stale rows.

Serialized per novel since 2026-08-16. Because materialize() is a novel-wide DELETE-then-rebuild, two concurrent runs were a data-loss race, not merely a stale read: jobs.py allows two chapters of one novel in flight, and the run that replayed first could commit last, wiping the other's projections and leaving nothing to re-derive them — analyze_chapter had already returned materialized: true. Recovery required a manual python -m pipeline.state.cli. Two changes close it: materialize() now takes a transaction-scoped pg_advisory_xact_lock(novel_id) before touching anything, and StateReplay.replay() accepts the transaction's own cursor so its four reads see one consistent snapshot. Previously each read checked out a separate pooled connection, so a chapter committed between them produced deltas whose chapter_id was missing from the map built by the first read — and those deltas were dropped with no log line.

Each run is logged to materialized_state_runs for auditability.

Invocation. analyze_chapter runs the materializer automatically after the chapter's persistence transaction commits, replaying through the novel's latest chapter (not just the one processed) so re-processing an earlier chapter with replace=true also rebuilds later projections. The standalone CLI (python -m pipeline.state.cli) remains available for manual backfills.

Eval Harness

backend/evals/ measures the write spine and read layer against a hand-written golden fixture novel, "The Lantern of Veyra" (10 chapters plus a hand-authored answer_key.yaml), rather than relying on eyeballing extraction output. Run the whole offline suite with: 

cd backend && .venv/bin/python -m pytest evals/ -s

This needs a real Postgres (for BM25/FTS and the schema) but no LLM API key or network access — extraction runs against the mock LLM.

Critic precision/recall

Seeds four known continuity violations (one per deterministic check) plus one clean draft against the seeded reads-test novel, then asserts ContinuityCritic flags every violation and produces no false positive on the clean draft — exact 1.0 precision and recall, deterministic.

Retrieval recall@k

Ingests the golden novel through analyze_chapter (mock LLM, hash embeddings, real chunking + Postgres full-text search), then runs 10 golden queries through the production reads.search.search() path. Floor: mean recall@8 ≥ 0.5.

Extraction fidelity (mock)

Exercises the ingest → projections → scoring plumbing end to end with the mock LLM. No thresholds — canned mock extraction isn't expected to match the answer key, only to produce well-formed scores.

Extraction fidelity (real LLM)

Gated behind RUN_LLM_EVALS=1 (spends API credits, skipped by default): ingests the golden novel with a real LLM and asserts per-category recall floors — characters/locations ≥ 0.75, objects ≥ 1.0, possessions ≥ 0.6, knowledge ≥ 0.5.

Entity resolution (pairwise)

evals/er_eval.py grades surface-form → entity assignment against the answer key's resolution: alias sets. Every unordered pair of surfaces is one judgement — same entity or not — so the metric works without the two id spaces corresponding. Precision and recall are not symmetric here: a false merge welds two entities together and drags every edge on both along with it, while a missed merge leaves a visible duplicate the merge endpoint can repair. The real-LLM gate fails on any false merge, and only holds recall to ≥ 0.6.

Surfaces the extractor never emitted are reported as coverage rather than scored as merge misses — that is an extraction failure, not a resolution one.

Duplicate-pair count

count_duplicate_pairs() needs no ground truth — it scores every entity pair with the canonicalizer's own _name_pair_similarity at its own LEXICAL_MATCH_RATIO, so it can be pointed at any ingested novel. It splits the count same-type vs cross-type, which is the number that matters: see the callout below.

Cross-type duplicates are the dominant failure mode. EntityCanonicalizer._load_roster loads candidates for one entity_type at a time, so when extraction files the same real-world thing as a character in one chapter and an object in the next, the canonicalizer never compares them. On a 3-chapter real-LLM ingest of a LitRPG novel this outnumbered same-type duplicates by an order of magnitude: 14 cross-type duplicate pairs against 1 same-type across 63 entities (Healer class existing simultaneously as a character, an object and a faction; System likewise).

Repair now exists; automatic detection does not. entity_merge previously refused any merge whose source and target disagreed on type, which made these unfixable by hand as well as by the pipeline. It now supports reclassifying merges (see Entity Merge), and GET /api/novels/{id}/entities/duplicates surfaces the candidates. What is still missing is cross-type candidate loading inside the canonicalizer, so these are found and fixed by review rather than prevented at ingest.
