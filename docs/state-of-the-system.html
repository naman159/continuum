State of the System

Where Continuum stands today, and where it needs to be to close the gap with SOTA.
branch: closing-the-gap-with-sota · 251 backend tests green · assessed 2026-06-10 · updated 2026-07-07 (state materializer wired in)

Continuum has built an excellent set of organs and has not yet connected the circulatory system. The relational + vector knowledge base is largely state-of-the-art, the extraction pipeline is deep and disciplined, and four advanced subsystems — hybrid retrieval, a continuity critic, a scene planner, and an event-sourced state materializer — are individually well-engineered and unit-tested. All four now have callers — the state materializer runs automatically at the end of every processed chapter, and the planner, retriever, and critic drive the generation loop — but several of the marquee tables they depend on have no producer, and the one component that would turn this from a continuity analyzer into the agentic writing system the research describes — a Drafter inside an orchestrated loop — does not exist. This page is the honest map of that gap.

TL;DR

The one-sentence version: the schema and the modules are ~80% of a SOTA design; the missing 20% is almost entirely integration, data-flow, and measurement, not new module quality.
  • What runs today is an analyzer. Ingest existing chapter prose → 12-pass LLM extraction → Postgres knowledge base → read-only React wiki. This path works end-to-end and is genuinely good.
  • What the research describes is a generator. Plan → Retrieve → Draft → Critique → Revise → Update, run by a deterministic orchestrator. The Drafter and the orchestrator do not exist.
  • The four advanced subsystems are no longer orphaned. state/ now runs automatically inside process_chapter; planner/, retrieval/, and critic/ are consumed by the generation loop (generation/loop.py).
  • The schema is one or two phases ahead of the extractor. temporal_constraints and the SVO/story-time columns on events have no producer at all. The bitemporal edges now fill automatically — the state materializer runs at the end of every processed chapter. canon_facts has a live producer (pass 13) with lock/contradiction semantics.
  • So half the critic is hollow. Three of its six checks query tables that are never populated, and the critic itself is never invoked because nothing produces the DraftChapter it consumes.
  • There is no way to know if any of this is working. No eval harness, no continuity metric, no retrieval recall measurement. "Closing the gap with SOTA" is currently unfalsifiable.

How to Read This

Every component is tagged with one of four states. The same vocabulary is used in the reality map, the scorecard, and the deep dives.

 Wired — built and on the live path  Orphaned — built & tested, imported nowhere  Schema-only — table/columns exist, no producer  Missing — not built at all

Each deep-dive section ends with a Where we stand → Where we need to be pair so the document doubles as a roadmap, not just a diagnosis.

The Core Gap I — Analyzer vs. Generator

The deep-research doc (continuity-arch-deep-research.md) describes an agentic novel-writing system. The code that actually runs is a continuity analyzer for prose written elsewhere. These are different products, and the ambiguity between them is the single most important thing to resolve, because it decides what to build next.

pipeline.py:process_chapter takes existing chapter text as input and ends by persisting structure. There is no generation anywhere in the flow. The planner, retriever, and critic were all built for the generator vision — yet the only thing that exists end-to-end is the analyzer. The piece that would make this a "writing system," the Drafter, is exactly the piece that is missing.

Decision required. Is Continuum (a) a continuity checker / story-bible generator over human- or externally-written prose, or (b) an end-to-end novel generator? Both are valid. But the near-term roadmap is completely different depending on the answer, and right now the codebase is hedging — paying the complexity cost of (b) while only shipping (a).

Where we stand

An analyzer wearing a generator's skeleton. Generator-oriented modules exist but nothing generates; the product that ships is the wiki.

Where we need to be

An explicit, written product decision. Recommended: analyzer-first — make the critic and retriever pay off over existing prose now, treat the Drafter as a later, eval-gated phase.

The Core Gap II — The Wiring Gap

Four sophisticated subsystems exist. A repository-wide import search confirms that pipeline.planner, pipeline.retrieval, pipeline.critic, and pipeline.state are imported nowhere outside their own packages and test suites. Each module independently fell into place; no one wired the loop. The orchestrator the research calls "the single most important structural element" is the missing keystone.

Deep Dive — Extraction Wired

This is the strongest part of the system and is meaningfully ahead of what the stale top-level architecture.md describes (it still says "6-pass"). The real pipeline runs 13 sequential passes per chunk:

chapter_summary · new_entities · entity_deltas · events · thread_updates
continuity_flags · relationship_updates · dynamics_updates · scene_segmentation
multi_granularity_summaries · knowledge_state_deltas · commitments · canon_facts

Followed by an intra-extraction dedup pass and an LLM canonicalizer with type-specific rules (the object rules correctly refuse to merge same-named items with different owners; the character rules demand a verbatim grammatical anchor before merging — both are thoughtful). Dedup now covers every name field (event factions, scenes, learnings, custom entity types), validates LLM group output against the actually-extracted names, merges trivially-equal names deterministically without an LLM call, and caps the roster sent per canonicalization call (CANONICALIZER_MAX_ROSTER, default 80) so per-chapter cost stays bounded as the cast grows. Custom entity types get aliases via entities.aliases. When dedup still gets it wrong, manual repair now exists: POST /api/novels/{id}/entities/merge merges a duplicate into its canonical twin in one transaction (no longer a CLI command — see pipeline/db/entity_merge.py). Duplicate relationship edges are also deduped at persist time. The mock-LLM path keeps the whole thing testable offline.

The gaps that matter

  • Events are not SVO triples. The events pass emits {description, event_type, impact_level, involved_*} — no subject/verb/object. So the SVO columns and any structured causal/temporal reasoning the schema anticipates cannot function.
  • Canon-fact pass is now wired. Pass 13 (canon_facts) proposes lockable world-facts (eye colour, magic costs, roles). persist_canon_facts() upserts on (novel_id, subject_entity_id, predicate); a locked fact contradicted by extraction becomes a continuity_flag (flag_type='canon_contradiction') instead of an overwrite. The Canon page lets users toggle the lock per fact via PATCH /api/novels/{id}/canon/{fact_id}.
  • No temporal-relation or story-time output. Events get neither a story_time_ordinal nor before/after links, so non-linear narration and timeline checks are impossible.
  • Possession/location are left implicit in event descriptions rather than emitted as typed deltas — which forces the brittle regex inference downstream (see Heuristic Inference).

Where we stand

  • 12 deep passes, dedup, canonicalization — high quality
  • Events are free-text; SVO / story-time / canon / temporal columns left empty

Where we need to be

  • Events as ordered SVO triples with story_time_ordinal + scene_id
  • Typed possession/location deltas; a canon-fact proposal pass; temporal before/after links

Deep Dive — Hybrid Retrieval Orphaned

The best-engineered module in the repo, and the one serving the fewest queries (zero). HybridRetriever.retrieve runs exactly the pipeline the research prescribes:

  1. Embed the query once (reused for dense search and MMR).
  2. BM25 + dense search per kind (chapter, scene, event) in parallel via a thread pool, with per-stage error capture.
  3. Reciprocal Rank Fusion (k=60) across all source/kind lists.
  4. Optional LLM cross-encoder rerank of the fused pool.
  5. MMR diversification (λ=0.7) down to query.k.

It even records per-stage timings and top-K snapshots into a debug dict — the seed of an observability story the rest of the system lacks. The BM25 backing (tsvector + GIN indexes with weighted fields) and HNSW vector indexes are already in the schema and populated for chapters/scenes/events.

The irony: meanwhile gather_plan_context (the planner's context builder) pulls "recent" material by pure ORDER BY chapter DESC LIMIT n recency — exactly the naive retrieval the research warns against — while this far better retriever sits unused two directories away. A built retriever serving no queries is pure liability: it rots and misleads readers of the docs.

Where we stand

A complete, instrumented hybrid stack with no caller. Planner context uses naive recency instead.

Where we need to be

  • A /api/search endpoint exposing it to the UI
  • gather_plan_context routes through it
  • (generator phase) it builds the Drafter's typed context bundle

Deep Dive — Continuity Critic Orphaned

The critic runs six typed checks and aggregates structured Findings with FAIL / WARN / INFO severities; a report "passes" iff there are no FAILs. The design is right — typed, queryable checks rather than a vibes-based "read it and tell me if anything is off" prompt. But it has two compounding problems.

1. It has no input producer. The critic consumes a DraftChapter of already-extracted claims (mentions, location/possession/knowledge claims, events, planned thread/commitment IDs). The dataclass docstring itself admits: "In the eventual pipeline this is populated by the Extractor running on the draft prose; in tests it's constructed directly." That adapter — prose → DraftChapter — does not exist. So the critic only ever runs in tests.

2. Half its checks query empty tables (see the dedicated scorecard below).

Where we stand

Six well-typed checks, never invoked, three of them querying tables with no producer.

Where we need to be

  • An extractor → DraftChapter adapter (reuse the 12-pass output)
  • Run as a post-extraction gate; persist + render findings in the wiki
  • Light up canon / temporal / possession tables so all six checks bite

Deep Dive — Scene Planner Orphaned

ScenePlanner.plan gathers a PlanContext (locked facts, pending commitments, active threads, recent summaries, recent events, main characters) and asks an LLM for a typed ChapterPlan of scenes — each with POV, location, threads to advance, commitments to plant/satisfy, target beat and word count. The mock path emits a deterministic two-scene plan so tests and USE_MOCK_LLM=true stay green. The ChapterPlan is explicitly intended as "the contract the Drafter must satisfy and the Critic will verify against."

Two issues: there is no Drafter to consume the plan, and the context it plans from is assembled by recency rather than relevance. The planner's locked_facts input from canon_facts is now populated by pass 13, so that blind spot is closed — but the planner still reasons from naive recency rather than the hybrid retriever.

Where we stand

Produces sound plans into the void; plans from naive-recency context. Locked-facts input is now populated (pass 13), but recency bias remains.

Where we need to be

Plan from retriever-built context, hand the ChapterPlan to a Drafter, and have the Critic verify the draft against the plan's declared threads/commitments.

Deep Dive — State Materializer Wired

EventReplay walks events in story order and derives character snapshots plus located_in and possesses facts; StateMaterializer persists them in a single transaction as a full novel-scoped rebuild (delete the novel's edge projection, re-derive from the event log, chain superseded_by_id), and is idempotent — stale edges from removed events do not survive. This is the event-sourcing core the research asks for, and it is well done.

process_chapter now invokes it automatically after each chapter's persistence transaction commits, replaying through the novel's latest chapter so a replace=true re-process of an earlier chapter also rebuilds later projections. Bitemporal edges are therefore populated on every freshly processed novel, and the critic's location/possession check has real data to read. The CLI (python -m pipeline.state.cli) remains for manual backfills of novels processed before this wiring landed.

There is also a deeper design tension here — see Dual Source of Truth. The materializer and the extractor both write character_states, with different notions of which layer is authoritative.

Where we stand

Correct, idempotent replay; runs automatically at the end of every processed chapter; bitemporal edges populated in practice.

Where we need to be

The sole writer of derived state — the extractor still writes character_states directly (see Dual Source of Truth).

Data Integrity — Dual Source of Truth for State

character_states is written by two different layers with different semantics:

  • The extractor writes one row per entity_delta directly from the LLM's per-chapter deltas (_persist_extraction).
  • The materializer rebuilds snapshots by replaying the event log (and seeds from the extractor's rows), DELETE-then-INSERT scoped to (character_id, chapter_id).

The research is explicit: event log = ground truth, snapshots = derived projection. But here deltas are always written and the event log is a partial, lossy shadow (events carry no SVO, no possession/location semantics). That inverts the intended architecture — today the deltas are authoritative and the event log cannot reconstruct them.

Where we stand

Two writers, no declared winner — and since the materializer now runs after the extractor on every chapter, replay-derived state partially overwrites delta-derived state in practice.

Where we need to be

Pick one. Recommended: make events authoritative — extractor emits rich events only, the materializer builds all snapshots and edges. Single writer, true time-travel.

Data Integrity — Heuristic Possession/Location Inference

event_replay.py infers item gain/loss by regex-matching English verb lists (took, gave, stole, …) against the event description, and assumes involved_characters[0] is the actor. For an engine whose entire value proposition is precision, deriving possession from verb-matching is the weakest link in the chain:

  • No negation handling ("did not take", "tried to take but failed").
  • No actor disambiguation — first-listed character is assumed to be the one acting.
  • Passive voice and multi-object sentences are mis-attributed.

The research is clear that these transitions should be extracted as typed deltas, not re-derived from prose downstream. The materializer should chain validity intervals; it should not be guessing semantics from verbs.

Where we stand

Possession/location semantics reconstructed by regex on free-text descriptions.

Where we need to be

Extractor emits explicit {actor, object, change: gain|loss} and {entity, location, since} deltas; replay just stitches intervals.

Data Integrity — Chapter Processing Is Not Atomic

process_chapter performs many independent commits: events are inserted one-by-one with commit=True, and each db.execute() opens its own transaction (see db/client.py — every fetch/execute borrows a connection and commits or rolls back on its own). A transaction() context manager exists and the materializer uses it correctly, but the main pipeline does not.

A failure midway through process_chapter leaves partial state — some events written, no commitments, scenes half-inserted — directly contradicting the research's "treat chapter generation as a database transaction: PLAN → DRAFT → CRITIQUE → REVISE → EXTRACT → COMMIT, no partial state escapes" discipline.

Where we stand

Dozens of per-statement commits per chapter; no rollback boundary; partial-failure states are possible and not detectable.

Where we need to be

One transaction per chapter (or per phase), idempotent re-runs, and a clean rollback on any failure.

Foundations — No Eval Harness Missing

The research grounds nearly every recommendation in measurement: retrieval recall@10 on a held-out scene set, continuity errors per 10k words, a 20–50 scene golden set with known canonical citations. None of this exists. There is no eval directory, no golden set, no continuity metric.

Without an eval harness, the branch name closing-the-gap-with-sota is unfalsifiable. There is no way to tell whether wiring the critic, fixing the extractor, or adding a drafter improves continuity — or regresses it. This should be built before the generator, not after.

Minimum viable eval: 20–50 hand-built scenes with (a) the canonically-correct passages a good retriever should surface, and (b) a handful of deliberately-seeded continuity errors a good critic should catch. Report recall@k and critic precision/recall in CI.

Foundations — Observability & Cost

A chapter already costs a lot of LLM calls: 13 extraction passes per chunk, plus intra-dedup, canonicalization, multi-summaries, scenes, knowledge, and commitments — before any planning, drafting, or critique. Prompt size is now bounded, at least: the canonicalizer roster is capped (CANONICALIZER_MAX_ROSTER) and extraction context selects mentioned + recent entities under CONTEXT_MAX_CHARACTERS/CONTEXT_MAX_LOCATIONS instead of dumping the full cast. Yet:

  • LLM_CONFIG is single-model; there is no tiering (cheap model for extraction/style, strong model for drafting) despite LiteLLM making this trivial.
  • No per-chapter token / cost / call-count logging. The research's "always-on observability" — token usage by tier, retrieval hit-rates, critic findings by category, commitment-pool age — is absent.
  • The retriever's per-stage debug timings are the only instrumentation in the codebase, and nothing consumes them.

Where we stand

Single model for everything; no cost or latency visibility; spend grows blindly with chapter count.

Where we need to be

Model tiering via LiteLLM; a per-chapter run record (tokens, cost, timings, finding counts); generalize the retriever's debug pattern across phases.

Foundations — Migration Hygiene

Schema is applied two ways at once: an idempotent schema.sql (run by init-db) and five hand-run migrate_*.py scripts. There is no version table and no migration framework. Fresh installs (full schema.sql) and incrementally-migrated databases will drift apart over time. Separately, the __EMBEDDING_DIM__ string-substitution bakes the embedding dimension in at init — changing embedding models later requires a manual column + index rebuild.

Where we stand

Idempotent schema + ad-hoc migration scripts, no version tracking, dimension locked at init.

Where we need to be

A single migration story (Alembic or a schema_version table); fold/retire the migrate_* scripts; document the embedding-dimension constraint and a re-index path.

Foundations — Docs Drift

The top-level architecture.md still describes a "6-pass" pipeline and lists none of critic/, planner/, retrieval/, or state/. The docs website (architecture.html) is much more current — it even documents those four advanced modules — but it presents them as part of the system without noting they are not yet wired. The repo's own CLAUDE.md mandates keeping the docs website current after every change; this page is part of closing that loop by stating the wiring status plainly.

Where we stand

architecture.md stale; docs site current but optimistic about what's connected.

Where we need to be

Retire or regenerate architecture.md; have the docs site mark wiring status (this page is the source of truth for that).

Roadmap (P0 → P5)

Ordered by leverage. P0–P3 deliver value on the analyzer path and are mostly integration; P4 makes everything measurable; P5 is the generator and should not start until P4 exists.

  • P0 · the keystone
    Build the orchestrator and make a chapter one transaction. Wire extract → materialize_state → critique → surface findings behind a single transaction boundary. This alone converts four islands into a system.
    Done when: processing a chapter automatically populates bitemporal edges and runs the critic; a mid-run failure leaves no partial state.
  • P1 · close the extractor → schema gap
    Make the empty tables fill. Emit SVO event triples + story_time_ordinal + scene_id; emit typed possession/location deltas; add a canon-fact proposal pass with a lock workflow; emit before/after temporal links.
    Done when: canon_facts, temporal_constraints, and the SVO columns are non-empty after processing, and all six critic checks can bite.
  • P2 · critic as a service
    Surface continuity findings in the product. Build the extractor → DraftChapter adapter, persist CritiqueReports, and render them in the wiki (a "Continuity" panel per chapter with FAIL/WARN/INFO and quotes).
    Done when: a user can see, per chapter, exactly which continuity rules fired and why.
  • P3 · wire the retriever
    Give the best module a consumer. Add /api/search; route gather_plan_context through HybridRetriever instead of naive recency.
    Done when: search works in the UI and the planner plans from relevance, not recency.
  • P4 · eval harness (do not skip)
    Make "closing the gap" measurable. A 20–50 scene golden set; report retrieval recall@k and critic precision/recall in CI; track continuity errors per 10k words.
    Done when: every change to retrieval/critic/extraction moves a number you can see.
  • P5 · the generator (eval-gated)
    Add the Drafter and Reviser inside the loop. Strongest model for prose, capped revision rounds, heterogeneous critic model when budget allows. Only after P4 proves the analyzer-side primitives are accurate.
    Done when: the full PLAN→…→COMMIT loop produces a chapter that passes the critic gate, with cost and quality tracked per chapter.
