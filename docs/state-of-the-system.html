The redesign is complete. This page is both the retrospective on how Continuum got here and the honest list of what's still genuinely open.

Continuum is a continuity analyzer, not a chapter generator — and, as of this page, that's a settled product decision rather than an open question. The system briefly grew a parallel chapter-authoring sub-system (a scene-level planner, a prose drafter, a critique-gated revision loop) while the SOTA schema and its four advanced subsystems — hybrid retrieval, a continuity critic, and an event-sourced state materializer among them — were still finding their callers. Once those subsystems were wired into the analyzer path (Plans 1–2 below) and it became clear the analyzer was the product, the authoring sub-system was torn down (Plan 3) rather than finished. What ships today is: ingest existing chapter prose (human-typed or agent-authored) → 13-pass extraction → one write spine that persists, materializes, and critiques every chapter → one read layer that serves the wiki, the API, and an MCP server for writing agents → an eval harness that makes every one of those claims falsifiable. This page tells that story and lists what remains genuinely open.

TL;DR

The one-sentence version: the analyzer-vs-generator ambiguity this page used to track is resolved — Continuum is the analyzer — and the three follow-on plans (write spine, read layer, teardown + evals) closed every integration and measurement gap this page previously flagged.
  • What runs today is the whole product, not a subset of one. Ingest chapter prose (human via the Process page/CLI, or an agent via the MCP save_chapter tool) → 13-pass LLM extraction → one Postgres write spine (persist → materialize → critique, all per-chapter) → a read layer serving the wiki, the API, and an MCP server. This path is end-to-end, transactional, and — new as of Plan 3 — measured.
  • The chapter-authoring sub-system this page used to track is gone, deliberately. A scene-level planner, a prose drafter, and a critique-gated revision loop were built and briefly wired into an orchestrated loop, then deleted (Task 2, Plan 3) once the product decision landed on analyzer-only. Nothing in the current codebase drafts prose; the critic and retriever now serve the analyzer exclusively.
  • The four advanced subsystems built during the SOTA branch are fully wired. state/ runs automatically inside analyze_chapter (phase 4); retrieval/ backs the wiki's Search page and the MCP search_story tool; critic/ runs and persists a critique for every analyzed chapter (phase 5); the fourth, the scene-level planner, had no analyzer-path use once the generator was cut, so it was deleted rather than kept orphaned.
  • The schema now matches the extractor exactly. temporal_constraints and the SVO/story-time columns on events had no producer and were removed 2026-07-11 (write-spine). Everything that remains in the schema has a writer: bitemporal edges fill via the state materializer, canon_facts via pass 13, and the write-spine's own new tables (state_deltas, critique_reports, critique_findings, schema_version) via the write spine itself.
  • The critic runs five checks, all with live producers. The sixth check, temporal_consistency, queried tables that were removed with the SVO/temporal columns and had no producer; it was deleted 2026-07-12 rather than left hollow. analyze_chapter builds a DraftChapter from the chapter's own extraction (critic/adapter.py: build_draft_from_extraction) and persists a critique_reports / critique_findings row set for every chapter.
  • There is now a way to know if any of this is working. backend/evals/ (Task Plan 3) runs a golden 10-chapter fixture novel through the real write spine and scores it: critic precision/recall exactly 1.0 against seeded violations, retrieval recall@8 ≥ 0.5 against Postgres full-text search, and (env-gated, real-LLM) extraction fidelity floors per entity category. "The redesign is complete" is now a falsifiable, tested claim, not an assertion.
  • Entity resolution is now measured too — and the measurement found a real hole (2026-08-06). A pairwise ER eval grades surface→entity assignment against hand-labelled alias sets, and a ground-truth-free duplicate counter can be pointed at any ingested novel. What it found: the canonicalizer loads its candidate roster one entity_type at a time, so the same real-world thing filed as a character in one chapter and an object in the next is never compared. On a 3-chapter real-LLM ingest that was 14 cross-type duplicate pairs against 1 same-type. Repair now exists (entity_merge reclassifies, and GET /entities/duplicates surfaces candidates); prevention does not. See Entity Resolution.

The Redesign I — The Decision: Analyzer, Not Generator

The deep-research doc (docs/research/continuity-arch-deep-research.md) describes an agentic novel-writing system. Earlier revisions of this page tracked an unresolved ambiguity: the code that actually ran was a continuity analyzer, but generator-shaped modules (a scene-level planner, a prose drafter, an orchestrated plan→retrieve→draft→critique→ revise→update loop) existed alongside it, wired into each other but not into the analyzer's own write spine.

That ambiguity is resolved. The 2026-07-11 analyzer-architecture spec made the call explicitly: Continuum is a continuity analyzer for prose written elsewhere — by a human via the Process page/CLI, or by a writing agent via the MCP save_chapter tool — not an end-to-end novel generator. Plans 1–2 spent the SOTA-branch subsystems (retrieval, critic, state materializer) on making the analyzer itself excellent: every chapter now gets materialized state and a persisted critique, not just chapters that happened to pass through a generation loop. Plan 3 then removed the chapter-authoring code entirely — the scene-level planner, the prose drafter, and the orchestrated revision loop — rather than leave it as unreachable dead weight. The style fingerprint that loop depended on survives as ingest-time chapter metadata (pipeline/style.py, computed and stored on every chapter regardless of source).

Decision, made. Continuum is a continuity checker / story-bible engine over human- or agent-written prose. The near-term roadmap (see Known Gaps / Next Steps) has no generator line item — if novel-length prose generation is ever wanted, it would be a new, separately-scoped product decision, not a resumption of the deleted loop.

Where we stood

An analyzer wearing a generator's skeleton. Generator-oriented modules existed and were briefly wired to each other, but not to anything a user could reach without generating a chapter.

Where we are now

Analyzer-only, by explicit decision. The critic and retriever pay off over existing prose; the generator-shaped code that used to hedge on a second product is gone.

The Redesign II — Read-Layer Consolidation

Earlier revisions of this page tracked a "wiring gap": pipeline.retrieval, pipeline.critic, and pipeline.state existed but were imported nowhere outside their own packages and test suites, each falling into place independently with no one module wiring them into a caller a user could reach. Plans 1–2 closed that gap for the three subsystems the analyzer needs; a fourth SOTA-branch subsystem — a scene-level chapter planner — had no analyzer-path use once the chapter-authoring loop it was built for was deleted, so it left with that loop rather than staying orphaned (see The Decision).

Deep Dive — Extraction Wired

This has always been the strongest part of the system. The pipeline runs 13 sequential passes per chunk:

chapter_summary · new_entities · state_deltas · events · thread_updates
continuity_flags · relationship_updates · dynamics_updates · scene_segmentation
multi_granularity_summaries · knowledge_state_deltas · commitments · canon_facts

Followed by an intra-extraction dedup pass and an LLM canonicalizer with type-specific rules (the object rules correctly refuse to merge same-named items with different owners; the character rules demand a verbatim grammatical anchor before merging — both are thoughtful). Dedup covers every name field (event factions, scenes, learnings, custom entity types, and the write-spine's state_deltas), validates LLM group output against the actually-extracted names, merges trivially-equal names deterministically without an LLM call, and caps the roster sent per canonicalization call (CANONICALIZER_MAX_ROSTER, default 80) so per-chapter cost stays bounded as the cast grows. Custom entity types get aliases via entities.aliases. When dedup still gets it wrong, manual repair exists: POST /api/novels/{id}/entities/merge merges a duplicate into its canonical twin in one transaction (see pipeline/db/entity_merge.py). Duplicate relationship edges are also deduped at persist time. The mock-LLM path keeps the whole thing testable offline, and is what the eval harness's default (non-RUN_LLM_EVALS) run exercises.

Resolved since the SOTA branch

  • Possession/location/knowledge/status are typed deltas, not inferred from prose. Pass 3 (state_deltas) emits a typed change log — kind (possession/location/knowledge/status), the affected entity, and a verbatim evidence quote — that the State Materializer replays deterministically. There is no more regex-over-event-descriptions inference step; see Typed State Deltas (this section used to be titled "Heuristic Inference" and describe the opposite problem).
  • Canon-fact pass is wired. Pass 13 (canon_facts) proposes lockable world-facts (eye colour, magic costs, roles). persist_canon_facts() upserts on (novel_id, subject_entity_id, predicate); a locked fact contradicted by extraction becomes a continuity_flag (flag_type='canon_contradiction') instead of an overwrite. The Canon page lets users toggle the lock per fact via PATCH /api/novels/{id}/canon/{fact_id}.

What's genuinely still not there

Events are still free-text ({description, event_type, impact_level, involved_*}), not SVO triples with story-time ordering — but the write-spine consolidation resolved this by removing the never-populated SVO/story_time_ordinal/narrative_order/scene_id columns from events rather than building a pass to fill them (see Schema Evolution). Non-linear narration and story-time-ordinal timeline checks remain out of scope unless a future spec reintroduces that surface deliberately.

Deep Dive — Hybrid Retrieval Wired

Resolved 2026-07-12, consumer simplified 2026-07-14. Previously the best-engineered module in the repo and the one serving the fewest queries (zero); it now has one production caller. HybridRetriever.retrieve runs:

  1. Embed the query once (used for dense search).
  2. BM25 + dense search per kind (chapter, scene, event) in parallel via a thread pool, with per-stage error capture.
  3. Reciprocal Rank Fusion (k=60) across all source/kind lists.
  4. Optional LLM cross-encoder rerank of the fused pool.
  5. MMR diversification (λ=0.7) down to query.k, ranking on the fused score and using embeddings only for the novelty penalty.

Ranking corrected 2026-08-14. Three defects made the "hybrid" ranking effectively dense-only:

  • MMR recomputed relevance as cosine similarity to the query embedding, discarding the fused score — so the one result BM25 and dense agreed on landed 7th of 8. It now ranks on the incoming fused score, max-normalized to share a scale with the novelty penalty.
  • Candidates missing an embedding fell back to a raw RRF score (~0.016) while embedded ones were scored on cosine (~0.6), making them unrankable. Both now use the same normalized scale.
  • plainto_tsquery ANDs every term, so natural-language queries matched nothing: "Jake fights the beast in the tutorial" returned 0 of 27 events. Relaxed to OR semantics over a sanitized websearch_to_tsquery; the same query now matches 22.

Results also carry the MMR score rather than the RRF score, so the emitted order is monotonic and the wiki's Search page stops rendering 0.02 for every row.

It records per-stage timings and top-K snapshots into a debug dict — still the only instrumentation of this kind in the codebase (see Observability & Cost). The BM25 backing (tsvector + GIN indexes with weighted fields) and HNSW vector indexes are in the schema and populated for chapters/scenes/events.

backend/reads/search.py::search() wraps HybridRetriever behind a _build_retriever(db) seam and backs both the wiki's Search page (GET /api/novels/{id}/search) and the MCP search_story tool — one implementation, two callers, which is exactly what the read-layer consolidation (above) was for. The retriever's per-scene-context caller from the chapter-authoring loop was removed along with that loop; nothing else in the analyzer path needed changing when it left, because the read layer never depended on it.

Deep Dive — Continuity Critic Wired

The critic runs five typed checks and aggregates structured Findings with FAIL / WARN / INFO severities; a report "passes" iff there are no FAILs. The design is right — typed, queryable checks rather than a vibes-based "read it and tell me if anything is off" prompt. It now has an input producer and five checks, all producer-backed — the sixth, temporal_consistency, was deleted 2026-07-12 rather than left querying a removed table.

1. It has an input producer, for every chapter. The critic consumes a DraftChapter of already-extracted claims (mentions, location/possession/ knowledge claims, events, planned thread/commitment IDs). critic/adapter.py:build_draft_from_extraction builds a DraftChapter straight from the chapter's own extraction — no second LLM pass — and analyze_chapter calls it (phase 5) for every chapter it processes, persisting the report via persist_critique. A sibling adapter, extract_draft_claims, still exists for building a DraftChapter from arbitrary draft text that hasn't been through extraction yet — it's what backs the MCP check_continuity tool, which lets a writing agent self-check a draft before calling save_chapter.

2. The one check that queried an empty/removed table was deleted (see the dedicated scorecard below).

Where we stood

Five well-typed checks with no input producer and no persistence — findings existed only for the duration of one request.

Where we are now

Invoked and persisted for every analyzed chapter, all five checks producer-backed, and findings render in the wiki (Continuity.tsx's Critique tab). The one open question: a chapter-processing failure in the critique phase today just logs and leaves critique: None in the result — the chapter still saves. That's a deliberate non-blocking design, not an oversight, but whether it should surface more loudly to the operator is still a fair question.

Retired — the Chapter-Authoring Sub-System

This section previously deep-dived a scene-level planning module: given locked canon facts, pending commitments, active threads, and recent context, it asked an LLM for a typed per-scene plan — POV, location, threads to advance, target beat and word count — intended as a contract for a prose-generation step to satisfy and the critic to verify against. It was well-typed and had a deterministic mock path, but nothing ever consumed its output outside of the authoring loop it was built alongside, and that loop was never the product.

Task 2 of Plan 3 (2026-07-14) deleted the module, its prose-generation counterpart, and the orchestration that sequenced them, in full — not disabled, not left orphaned behind a flag. The one piece of that sub-system worth keeping, a deterministic per-chapter prose fingerprint (sentence length, dialogue ratio, POV person, exclamation rate), was extracted into pipeline/style.py and is now computed at ingest time for every chapter — human- or agent-authored alike — and stored on chapters.style_fingerprint as voice metadata for the wiki, independent of any authoring pipeline.

Deep Dive — State Materializer Wired

StateReplay folds typed state_deltas (chapter order, insertion order) — not a walk over free-text events — and derives character snapshots plus located_in and possesses facts; StateMaterializer persists them in a single transaction as a full novel-scoped rebuild (delete the novel's edge projection, re-derive from the deltas, chain superseded_by_id), and is idempotent — stale edges from removed deltas do not survive. This is the event-sourcing core the research asks for, and it is well done.

analyze_chapter now invokes it automatically after each chapter's persistence transaction commits, replaying through the novel's latest chapter so a replace=true re-process of an earlier chapter also rebuilds later projections. Bitemporal edges are therefore populated on every freshly processed novel, and the critic's location/possession check has real data to read — and, since the critique phase now runs immediately after materialization in the same call, it reads that data the same chapter it was produced. The CLI (python -m pipeline.state.cli) remains for manual backfills of novels processed before this wiring landed.

The dual-writer tension formerly described here is resolved — see Dual Source of Truth. The materializer is now the sole writer of character_states; the extractor only reads it for context.

Where we stand

Correct, idempotent replay; runs automatically at the end of every processed chapter; bitemporal edges populated in practice; sole writer of character_states as of 2026-07-12 (see Dual Source of Truth).

Where we need to be

Here — this is done.

Critic Check Scorecard

All five checks have live producers, but having a producer and being able to fire are different things, and this table used to conflate them. A 2026-08-16 audit traced each check end-to-end from pipeline.py and found that on the ingestion spine three of the five were structurally incapable of emitting a finding, because build_draft_from_extraction() hardcoded the very fields they gate on: learned_this_chapter: True, possession_claims: [], planned_thread_ids: [], planned_commitment_ids: []. Each hardcode was a defensible fix for a real false positive; cumulatively they removed the signal with the noise.

Resolved 2026-08-17 by CRITIQUE_CLAIMS (default extract). The missing inputs never needed a new extraction pass — extract_draft_claims() already produced exactly them for the MCP path, at one LLM call per chapter rather than per chunk. The spine now uses it by default, so knowledge and location/possession claims are real rather than hardcoded. Data Integrity — Dual Source of Truth for State Resolved 2026-07-12

Resolved 2026-07-12. This section previously described character_states being written by two different layers with conflicting semantics — the extractor writing one row per entity_delta directly (_persist_extraction), and the materializer separately rebuilding snapshots by replaying state_deltas. That is no longer the case: the materializer (pipeline/state/materializer.py) is now the sole writer of character_states — see its own comment, "character_states: sole writer — novel-scoped DELETE-then-INSERT." The extractor and canonicalizer only read character_states for context; they no longer write to it. Left in place below for history rather than deleted.

Where we stood

Two writers, no declared winner — and since the materializer ran after the extractor on every chapter, replay-derived state partially overwrote delta-derived state in practice.

Where we are now

Single writer: StateMaterializer derives all character_states rows from state_deltas. The extractor no longer writes the table directly.

Data Integrity — Typed State Deltas Resolved 2026-07-13

Resolved (write-spine, Plan 1). This section previously described event_replay.py inferring item gain/loss by regex-matching English verb lists (took, gave, stole, …) against free-text event descriptions, and assuming involved_characters[0] was the actor — no negation handling, no actor disambiguation, passive voice mis-attributed. That module and that approach are both gone.

Extraction pass 3 (state_deltas) now emits explicit, typed changes directly: {kind: possession|location|knowledge|status, subject, object/location/attribute, change, quote}, each with a verbatim evidence quote from the chapter text. StateReplay (pipeline/state/replay.py) folds this log in narrative order (chapter.number, delta.ordinal, delta.id) into snapshots and bitemporal edges — no verb lists, no actor-position guessing, no free-text re-derivation. The delta is the semantic claim; replay only stitches validity intervals.

Where we stood

Possession/location semantics reconstructed by regex on free-text event descriptions.

Where we are now

Extractor emits explicit {kind, subject, object/location, change} deltas with evidence quotes; replay just stitches intervals. This is done.

Data Integrity — Chapter Persistence Is Atomic Resolved 2026-07-13

Resolved (write-spine, Plan 1). This section previously described analyze_chapter making many independent per-statement commits — events inserted one-by-one with commit=True, each call opening its own transaction — so a mid-run failure could leave partial state (some events written, no commitments, scenes half-inserted).

The core persistence phase — ingest, entities, events, relationships, summaries, scenes, knows-edges, commitments, canon facts, state deltas — now runs inside one DBClient.session() block, bound to a single pooled connection. DBSession accepts the same commit= keyword the older per-statement helpers pass, but silently ignores it — commit/rollback ownership belongs entirely to the enclosing session, which commits once on clean exit and rolls back the whole phase on any exception (see Reference: DBClient / DBSession). A failure inside that block now leaves no partial chapter, not a partially-written one.

Amended 2026-08-16. The single-transaction claim above was correct, but until this date the best-effort try/except blocks inside persist_extras.py undermined it from the other direction. Catching a statement error and continuing on the same connection does not recover anything — PostgreSQL has already aborted the transaction, so every later statement fails with InFailedSqlTransaction, and a COMMIT issued against an aborted transaction is silently downgraded to ROLLBACK rather than raising. One bad scene row therefore cost the whole chapter, either loudly with a misleading "current transaction is aborted" error, or — when no later statement happened to run — silently, with analyze_chapter returning a success payload whose chapter_id pointed at nothing. Each block now runs inside a SAVEPOINT via DBSession.savepoint(), so a failed row rolls back alone and the chapter survives, which is what the "log and continue" comments always intended.

The two phases that run after that commit — MATERIALIZE and CRITIQUE — are deliberately not inside the same transaction: they're derived, idempotent, and re-runnable, so a failure there is caught, logged, and reported via materialized: False / critique: None in the result rather than rolling back an already-saved chapter. That's a design choice, not the atomicity gap this section used to describe.

Where we stood

Dozens of per-statement commits per chapter; no rollback boundary; partial-failure states were possible and not detectable.

Where we are now

One transaction for the entire persist phase; materialize/critique run after commit, independently retryable. This is done.

Data Integrity — Agent Write Gate Resolved 2026-08-24

Resolved. This page used to carry an unwritten but real gap: Continuum had no hard bounds on writing agents. Every continuity control in the system was advisory only — check_continuity's enforcement mechanism was a sentence in its docstring telling an agent to call it before save_chapter, nothing stopped an agent from skipping straight to save_chapter, the critic ran after the extraction transaction had already committed (so by the time it had a verdict the contradictory chapter was already canon), and a FAIL finding changed nothing — save_chapter returned {"ingested": True, ...} with the critique attached as data, the same shape whether the critique passed, failed, or threw. settings.critic_enabled = False could also disable the critic entirely with no replacement check. The only actual hard bound was replace=False, which only prevents overwriting an existing chapter.

pipeline/gate.py::gate_agent_draft() now sits in front of extraction for every source == 'agent' write. It runs the cheap draft-claims critic path — one LLM call for extract_draft_claims(), then ContinuityCritic.critique() — against the raw text before any of the 13-pass extractor runs. A FAIL parks the draft in a new draft_submissions table and refuses the write; a critic exception is treated the same way (reason: "critic_error"), and a disabled critic refuses outright without parking anything, since there's no verdict to park (reason: "critic_disabled") — an outage cannot become a free pass. save_chapter's return contract now reflects this: {"ingested": false, "status": "pending_review", "submission_id", "reason", "fails", "warns"} on refusal, the pre-existing success shape otherwise. Human writes are completely untouched — the gate is keyed strictly on source.

The human is the only override, and it is not a silent one. The wiki's Review page (/novels/{id}/review) lists parked drafts; accepting one re-runs the full pipeline with a bypass flag that only pipeline/drafts.py::accept_submission is allowed to set (it is not exposed as a request field, CLI flag, or MCP parameter anywhere else), and writes the draft's blocking findings through to continuity_flags — a human-blessed contradiction stays visible in the Continuity view rather than being silently absolved. Rejecting just marks the row; the agent has to revise and resubmit, which supersedes the earlier parked row for that chapter.

Where we stood

Every continuity control an agent could reach was advisory: a docstring telling it to self-check, a post-commit critique that couldn't stop anything, and a success response that looked identical whether the draft passed, failed, or the critic errored.

Where we are now

A chapter row in chapters means it passed continuity, full stop. Refusal happens before extraction, fails closed on any critic problem, and the only path around it is a human acting through the Review queue — recorded, not absorbed. knowledge_state_check's word-overlap matching still bounds how precise the gate can be; see Known Gaps / Next Steps.

Foundations — Eval Harness Built 2026-07-14

Resolved (Plan 3, Task Plans 3–5). This section previously read "Missing": no eval directory, no golden set, no continuity metric, so nothing could tell you whether a change to retrieval, the critic, or the extractor improved continuity or regressed it. backend/evals/ now exists and is exactly the minimum-viable eval this section used to call for — a hand-built golden set with known-correct answers, scored automatically.

The golden set is a full 10-chapter fixture novel, "The Lantern of Veyra" (backend/evals/golden/), with a hand-authored answer_key.yaml covering entities, possessions, knowledge, hand-labelled alias sets (resolution:), and ten retrieval queries with known expected chapters. Four evals run against it:

  • Critic precision/recall — four seeded continuity violations (one per deterministic check) plus one clean draft against the seeded reads-test novel; asserts the critic flags every violation and produces zero false positives. Both metrics assert exactly 1.0 — deterministic, no LLM in the loop.
  • Retrieval recall@8 — ingests the golden novel through the real analyze_chapter write spine (mock LLM, hash embeddings, real Postgres full-text search), then runs the golden queries through the production reads.search.search() path. Floor: mean recall@8 ≥ 0.5.
  • Extraction fidelity — a mock-mode plumbing test always runs (ingest → projections → scoring, no thresholds); a real-LLM variant, gated behind RUN_LLM_EVALS=1 so it doesn't spend API credits by default, asserts per-category recall floors (characters/locations ≥ 0.75, objects ≥ 1.0, possessions ≥ 0.6, knowledge ≥ 0.5).
  • Entity resolution (added 2026-08-06) — grades surface-form → entity assignment against the answer key's resolution: alias sets. Every unordered pair of surfaces is one same-entity-or-not judgement, so the metric works without the fixture's ids and the DB's ids corresponding. Mock mode checks plumbing; the RUN_LLM_EVALS=1 variant fails on any false merge and asserts recall ≥ 0.6, type accuracy ≥ 0.8, and zero cross-type duplicates. Alongside it, count_duplicate_pairs needs no ground truth at all and can be pointed at any ingested novel — see Entity Resolution.

Run the whole offline suite with cd backend && .venv/bin/python -m pytest evals/ -s — see Reference: Eval Harness for the module-to-eval table.

Foundations — Entity Resolution Measured 2026-08-06, one gap still open

Extraction quality was measured before resolution quality was, which hid the more expensive error. An entity the extractor misses is a hole; an entity it splits in two is a wrong answer that looks like a right one — the wiki shows two characters, the MCP tools return half a history each, and nothing flags it. Two new measurements close that blind spot, and they answer different questions on purpose:

Pairwise ER eval (needs ground truth)

evals/er_eval.py::run_resolution_eval scores every unordered pair of surface forms as one same-entity-or-not judgement against answer_key.yaml. Precision and recall are not symmetric: a false merge welds two entities together and drags every edge on both along with it, while a missed merge leaves a visible duplicate the merge endpoint can repair. The real-LLM gate therefore fails on any false merge but holds recall only to ≥ 0.6. Surfaces the extractor never emitted are reported as coverage, not scored as merge misses — that is an extraction failure, not a resolution one.

Duplicate-pair count (needs none)

evals/er_eval.py::count_duplicate_pairs → pipeline/db/duplicates.py scores every entity pair with the canonicalizer's own _name_pair_similarity at its own LEXICAL_MATCH_RATIO, so a listed pair is one the canonicalizer would have called a match had it compared them. No answer key required, so it runs against any ingested novel — and it is the same function the /entities/duplicates endpoint serves, so the eval and the product cannot drift apart.

Repair path

merge_entities used to raise unless source and target shared an entity_type. It now treats a cross-type merge as a reclassification: entity-level references repoint, event involvement moves columns, and the source's type-specific rows die with its typed row as artifacts of the misclassification. Covered against real Postgres by pipeline/db/tests/test_entity_merge_integration.py, because the fake-DB tests assert which statements run and cannot catch a foreign-key violation.

The open gap: cross-type duplicates are found and repairable, but not prevented. EntityCanonicalizer._load_roster loads candidates one entity_type at a time, so a character is never compared against an object. When extraction files the same real-world thing under two different types across chapters, nothing in the pipeline can reach it. On a 3-chapter real-LLM ingest of a LitRPG novel this outnumbered same-type duplicates by an order of magnitude: 14 cross-type duplicate pairs against 1 same-type across 63 entities (Healer class existing simultaneously as a character, an object and a faction; System likewise). LitRPG is an adversarial case for typing — but the mechanism is generic, and the fix (cross-type candidate loading in the canonicalizer) is listed in Known Gaps.

Foundations — Observability & Cost Still Open

A chapter already costs a lot of LLM calls: 13 extraction passes per chunk, plus intra-dedup and canonicalization — before scenes, knowledge, and commitments are even persisted. Prompt size is bounded: the canonicalizer roster is capped (CANONICALIZER_MAX_ROSTER) and extraction context selects mentioned + recent entities under CONTEXT_MAX_CHARACTERS/CONTEXT_MAX_LOCATIONS instead of dumping the full cast. This part of the picture hasn't changed since the redesign, and is a genuinely open gap:

  • LLM_CONFIG is single-model — no tiering (cheap model for extraction/style, stronger model where it would matter) despite LiteLLM making this straightforward.
  • No per-chapter token / cost / call-count logging. There's no run record answering "what did this chapter cost" — token usage, retrieval hit-rates, critic finding counts by category.
  • The retriever's per-stage debug timings are still the only instrumentation of this kind in the codebase, and nothing outside the retriever itself consumes them.

Where we stand

Single model for everything; no cost or latency visibility; spend grows blindly with chapter count.

Where it would help to go next

Model tiering via LiteLLM; a per-chapter run record (tokens, cost, timings, finding counts); generalize the retriever's debug pattern across the write spine's other phases.

Known Gaps / Next Steps

Everything this page used to list as a gap is resolved except the items below — carried forward because they're still genuinely true, not because the list needs padding. There is no generator, chapter-authoring, or orchestrator item here: that direction was deliberately closed off by the analyzer-only decision (see The Decision), not left as a future phase.

  • Critic precision is not a precision measurement
    critic_eval's precision cannot fall below 0.8 by construction. It scores 4 positive cases and 1 negative, and only the single clean draft can produce a false positive; a positive case where the critic emits findings from the wrong check counts as a false negative, never a false positive. So a degenerate "flag everything" critic scores precision 0.8 / recall 1.0. Deliberately left until after the 2026-08-17 CRITIQUE_CLAIMS change, so the rescoring is done against checks that can actually fire rather than tuned against three inert ones.
    Done when: scoring is per finding — each emitted finding a TP if it matches a seeded violation on (check, character, quote) and an FP otherwise — against a negative set materially larger than one clean draft.
  • Planner-dependent checks
    thread_coverage and the planned half of commitments have no live caller. Both gate on planned_thread_ids / planned_commitment_ids, which every current caller passes as []. This is dormancy by design, not breakage: an analyzer-only system produces no plan to check a draft against. Note thread_coverage also builds event_ids from an id field neither adapter attaches, so if a planner were wired up today it would warn on every thread unconditionally — fix that at the same time.
    Done when: either a planner supplies the ids and the id plumbing is fixed, or both branches are deleted rather than left as latent false positives.
  • Cross-type duplicate prevention
    EntityCanonicalizer._load_roster loads candidates one entity_type at a time, so an entity filed as a character in one chapter and an object in the next is never compared, let alone merged. Measured (14 cross-type pairs vs 1 same-type on a 3-chapter real-LLM ingest) and repairable by hand (GET /entities/duplicates + cross-type merge_entities), but not prevented at ingest. See Entity Resolution.
    Done when: the canonicalizer considers candidates across entity types (or a post-ingest pass does), and the real-LLM ER eval's cross_type_count == 0 assertion holds on a novel that isn't the hand-written fixture.
  • Observability & cost
    No per-chapter cost/token accounting, no model tiering. A chapter is 13 extraction passes plus dedup, canonicalization, multi-summaries, scenes, knowledge, and commitments, all on one model (DEFAULT_MODEL). See Observability & Cost.
    Done when: a per-chapter run record exists (tokens, cost, timings, finding counts) and low-stakes passes can route to a cheaper model via LiteLLM.
  • Embedding-dimension migration path
    __EMBEDDING_DIM__ is baked in at init-db time. Changing embedding models later still requires a manual column + index rebuild; nothing documents the procedure. See Migration Hygiene.
    Done when: there's a documented (or scripted) re-index path for changing EMBEDDING_DIMENSIONS/EMBEDDING_MODEL on an existing database.
  • Job tracking is in-memory
    Async chapter-processing job status doesn't survive a server restart and doesn't scale horizontally (backend/api/jobs.py, a module-level dict). Documented as a known limitation in Reference: Chapter Processing, not silently papered over.
    Done when: job state moves to the database or a queue, if multi-worker deployment is ever needed.
  • The write gate's precision is bounded by word-overlap matching
    knowledge_state_check matches a draft's knowledge claims against stored knows_edges facts by word overlap, not embedding similarity — its own docstring names the fix. The stored fact_description and the draft-claim's fact_description come from two independent LLM calls that rarely agree verbatim, so this is the check that decides whether an agent write gets refused for "knowing" something it shouldn't. New as of the agent write gate (2026-08-24) — before this, the check ran but nothing downstream of it could refuse a write, so its precision ceiling was invisible in practice. See Agent Write Gate.
    Done when: check_knowledge_state matches on embedding similarity (or another semantic measure) instead of words_overlap().
  • The MCP write path can't be exercised without live LLM calls
    mcp_server/queries.py::save_chapter hardcodes use_mock_llm=None on its call into analyze_chapter — there's no parameter to force mock mode from the MCP tool surface. Every accept-path test that needs to avoid spending real API credits (the write-gate refusal tests, the Review-page accept/reject tests) has to monkeypatch around it rather than pass a flag.
    Done when: save_chapter either accepts a mock-mode override, or reads one from settings the way the CLI path does, so exercising the MCP write path in a test doesn't require monkeypatching analyze_chapter.
  • Test-fixture duplication
    The write gate's tests copy fixtures instead of sharing them. The _force_mock_llm autouse fixture that wraps analyze_chapter to avoid live LLM calls is defined identically in both pipeline/tests/test_drafts_resolution.py and api/tests/test_drafts.py, and the db/seed_novel conftest pair — copied to stand up Postgres-backed drafts tests — now exists in three places: reads/tests/conftest.py (original), pipeline/tests/conftest.py, and mcp_server/tests/conftest.py, each one explicitly commented as mirroring the others rather than importing from one.
    Done when: both fixtures move to one shared location (a top-level conftest.py or a small shared test-support module) and the copies are deleted.
