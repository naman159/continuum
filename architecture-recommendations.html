Continuum — Architecture Recommendations

Closing the gap between our current pipeline and SOTA long-form narrative AI systems.

Based on a comparison of architecture.md against continuity-arch-deep-research.md

The Situation in One Paragraph

Our current PostgreSQL + pgvector pipeline is roughly 80% of the right architecture for a continuity-aware novel writing system. The relational core, entity extraction, and per-chapter snapshots are aligned with how state-of-the-art academic systems (DOC, DOME, SCORE, StoryWriter, CFPG) and the best industry tools (Sudowrite, novelcrafter, NovelAI) approach the problem. The remaining 20% is what determines whether the system can actually prevent continuity errors instead of just describing them after the fact.

Continuity is a state-management and retrieval problem, not a prompting problem. The LLM cannot reliably track "who knows what" from raw text — even Claude Opus only reaches 69% on theory-of-mind benchmarks vs. a 92% human baseline. We must externalize knowledge state into typed tables and let the LLM focus on prose.

1. Critical Changes — Highest ROI

These four additions close the largest accuracy gaps in current LLM long-form generation. Every one is a small, additive change to our existing schema — none requires rewriting what we have.

1.1 knows table — Character Knowledge Graph Critical

What it entails A new edge table tracking which character knows which fact, when they learned it, and how certain they are. This is the explicit "theory of mind" representation our current schema lacks entirely. 
knows(
  character_id      UUID REFERENCES characters,
  fact_id           UUID,
  learned_chapter   INT,
  source_event_id   UUID REFERENCES events,
  source_type       TEXT,  -- dialogue | observation | inference
  certainty         FLOAT,
  shared_with       UUID[]
)
Every chapter, the extractor adds rows ("in this scene, Aelric learns Mira is his sister"). The Continuity Critic queries this whenever a character says something implying knowledge of a fact.
Why this matters for the AI writer This is the single most under-served continuity dimension in every product on the market today. Theory-of-mind errors — characters knowing things they shouldn't, or forgetting things they were told — are one of the two dominant failure modes (per the ConStory-Bench 2026 evaluation across GPT-5 and Claude-class models). The KNP benchmark shows even the best LLM reaches only 69% accuracy from raw text. By externalizing this into a typed table, we move it from "LLM guesswork" to "deterministic SQL check." This single mechanism eliminates the largest class of continuity errors LLMs make.

1.2 Bitemporal Validity Intervals on Edges Critical

What it entails Our current relationships table overwrites prior facts. Adopt the Graphiti pattern — invalidate, don't delete. Add since_chapter and until_chapter to relationships, and create new edge tables for location and possession: 
relationships ADD since_chapter, until_chapter
located_in(entity_id, location_id, since_chapter, until_chapter)
possesses(character_id, object_id, since_chapter, until_chapter)
When a fact is contradicted by a later chapter, set until_chapter on the old row and append a new one. The history stays intact.
Why this matters for the AI writer Bitemporal state is what makes time-travel queries possible: "where was Aelric as of chapter 7?", "what items did Mira possess before the betrayal?". Without this, retroactive edits to early chapters silently corrupt later-chapter state. With this, the Drafter can correctly reason about character state at any narrative point — including flashbacks. Zep/Graphiti's research (94.8% vs. 93.4% on MemGPT's own benchmark, scaling to 98.2% with gpt-4o-mini) shows bitemporal models are the production-grade memory primitive.

1.3 commitment Table — Foreshadow/Payoff Triples Critical

What it entails Implement the CFPG framework (arXiv 2601.07033, 2026). Every foreshadow becomes a structured (F, T, P) triple — Foreshadow, Trigger condition, Payoff — maintained in a "commitment pool": 
commitment(
  id                    UUID PK,
  foreshadow_text       TEXT,
  foreshadow_chapter    INT,
  trigger_predicate     JSONB,
  payoff_text           TEXT,
  payoff_chapter        INT NULL,
  status                TEXT,   -- pending | satisfied | broken
  weight                FLOAT
)
Our existing continuity_flags stays — it catches inconsistencies after the fact. commitment is proactive: it tracks Chekhov's guns that are still on the wall.
Why this matters for the AI writer This is the cleanest formalism in the literature for "Chekhov's gun must fire" — and it is absent from every consumer product surveyed. The Planner agent will read the pending pool before planning each chapter and decide which to advance or satisfy. The Critic flags broken commitments (trigger met but no payoff fired). The result: foreshadows actually get paid off; planted details actually matter; the reader's promised resolutions actually arrive. This is the difference between a novel that feels deliberate and one that feels meandering.

1.4 Hybrid Retrieval — BM25 + Dense + RRF + Cross-Encoder Rerank Critical

What it entails Replace our pure pgvector IVFFlat search with a hybrid pipeline:
  1. BM25 over chapter passages, scene summaries, event payloads — catches literal token matches (proper nouns, item names, rule names)
  2. Dense vector search via pgvector HNSW — catches semantic similarity and paraphrase
  3. Reciprocal Rank Fusion (k≈60) — combines both without score-normalization headaches
  4. Cross-encoder rerank (BGE-reranker-v2 or Cohere rerank-3) — final precision pass on top ~50 → top ~10
  5. MMR diversification (λ≈0.7) — avoid five near-duplicate passages
Also switch IVFFlat → HNSW indexes for better recall.
Why this matters for the AI writer Pure embedding retrieval reliably misses the literal tokens — character names, place names, item IDs — that continuity errors most depend on, and reliably surfaces "thematically similar but canonically wrong" passages. The phrase "the dagger" in chapter 3 and "Aelric's dagger" in chapter 17 will not collide under pure cosine similarity. BM25 catches that. Cross-encoder rerank catches the rest. The research calls this "the single highest-leverage change you can make beyond what you have today."

2. Important Changes — Medium Term

2.1 Event Log as Ground Truth (Event Sourcing) Important

What it entails Flip the data model. Today, character_states is primary truth. Going forward: events are the append-only ground truth, character_states is a derived projection. A materialize_state(chapter_id) worker replays the event log from chapter 1 through N to produce/update state snapshots.
Why this matters for the AI writer Three wins for free: (a) time-travel queries — "character X's possessions as of chapter 14" is a derived query, not a separate snapshot lookup; (b) bitemporal auditability — "at the time we wrote chapter 20, what did we believe was true?"; (c) retroactive editing — fix chapter 3 and regenerate downstream state cleanly. This is the canonical pattern for narrative state and unblocks everything from non-linear narration (flashbacks) to multi-arc rollback.

2.2 canon_fact Table with Locked Flag Important

What it entails A new table for immutable story-world facts independent of time — physical laws, magic system rules, geography, character birth dates, eye color: 
canon_fact(
  id, kind, subject_entity_id, predicate, value,
  source_chapter, confidence, locked BOOL
)
High-stakes facts get locked = true. Any contradiction is a hard FAIL from the Continuity Critic.
Why this matters for the AI writer LLMs silently mutate small details under generation pressure — eye colors drift, magic systems get bent to suit the scene, ages quietly shift. Locked canon facts are the seatbelt: a deterministic check that catches these before the chapter commits. This is what novelcrafter's "hidden sub-details" and the academic literature's "immutable canon layer" both reach for.

2.3 Multi-Granularity Summaries Important

What it entails Today we generate one ~300-token chapter summary. The research recommends three granularities per chapter:
  • One-sentence (~50 chars) — for high-level navigation
  • One-paragraph (~150 words) — for recent-chapter context
  • Full-chapter (~500 words) — for arc-level context
Why this matters for the AI writer Hierarchical compression follows the GraphRAG pattern at the narrative scale. When the Drafter writes chapter 30, it needs full-resolution context on chapter 29, paragraph-resolution on chapters 26–28, and one-sentence resolution on chapters 1–10. This is how you stay within token budgets without losing the long-range plot signal. Without it, you're either summarizing on the fly (slow, lossy) or stuffing everything into context (expensive, "lost in the middle").

2.4 Scene-Level Segmentation Important

What it entails We chunk by tokens (sliding window), but have no concept of narrative scene boundaries. Add: 
scene(
  id, chapter_id, scene_index,
  pov_character_id, location_id, time_anchor,
  present_characters UUID[],
  summary, embedding VECTOR(1536)
)
Extract these per chapter during the existing extraction pass.
Why this matters for the AI writer Scenes are the natural unit of narrative work: a scene has a POV, a location, a time, a set of present characters, and an emotional beat. Token chunks have none of these. Once we segment into scenes, the Retriever can filter on "scenes where Aelric is POV and Mira is present" — a query impossible against raw chunks. It also gives the eventual Scene Planner agent a natural target unit.

2.5 temporal_constraint Edges Important

What it entails A table of explicit temporal relations between events: 
temporal_constraint(
  event_a_id, event_b_id,
  relation TEXT,   -- before | after | simultaneous | caused_by
  certainty FLOAT
)
Plus dual time representation on events: story_time_ordinal (in-world ordering) alongside narrative_order (publication order).
Why this matters for the AI writer This is how DOME's "Temporal Conflict Analyzer" catches "character was in Paris and Rome on the same Tuesday"-type errors. SAT-style constraint propagation over the constraint set surfaces impossibilities before commit. It also unlocks non-linear narration — flashbacks can have an earlier story_time but a later narrative_order, and the system still reasons about them correctly.

3. Deferred — Build Later

These are explicitly recommended not to build right now.

3.1 Agentic Generation Layer (Planner, Drafter, Critic) Defer

What it entails A 7-agent pipeline: Architect, Scene Planner, Retriever, Drafter, Continuity Critic, Style Critic, Extractor/State Updater. Phase-gated, deterministic orchestration.
Why we wait The current project is the extraction and knowledge-base layer — the foundation that the agentic generation layer would sit on top of. Building the agents before the knowledge base is solid leads to garbage-in/garbage-out. The research's recommended build order puts schema first (Phase 1), retrieval second (Phase 2), and the Scene Planner third (Phase 3). We finish Phase 1 before moving up.

3.2 External Graph Database (Neo4j / Memgraph) Skip

What it entails Migrating graph queries to a dedicated graph database with Cypher.
Why we skip it Research is explicit: at novel scale (under 10,000 entities), Postgres edge tables + recursive CTEs are sufficient. The operational overhead of a second database is not worth it until graph traversal becomes a measured bottleneck. Stay in Postgres.

3.3 Fine-Tuning / LoRA for Voice Defer

Why we wait A good architecture around Claude Opus or GPT-5 beats a fine-tuned 70B in coherence — by a wider margin than most expect. Defer LoRA until we have ~50k+ words of confirmed in-voice prose, at which point sample-conditioning becomes the cheaper path to style stability.

3.4 Free-Form Multi-Agent Debate Never

Why we skip it Slower, more expensive, and rarely beat phase-gated pipelines on long-form narrative. The DOC, DOME, StoryWriter, and Novel-OS papers all converge on deterministic state-machine orchestration with hard quality gates. Don't build debate loops.

6. Suggested Build Order

Six phases, roughly 8–12 weeks for the full critical path.

Phase 1 — Schema Upgrade (1–2 weeks)

  • Add knows, commitment, canon_fact, located_in, possesses, scene, temporal_constraint tables
  • Add bitemporal columns (since_chapter, until_chapter) to relationships
  • Add locked flag column to canon-relevant rows
  • Add multi-granularity summary columns to chapters
  • Switch IVFFlat indexes to HNSW
  • Backfill: re-run extractor on prior chapters with expanded schema

Phase 2 — Hybrid Retriever (1–2 weeks)

  • Add BM25 (Postgres full-text or external — tantivy / Meilisearch)
  • Implement RRF fusion + cross-encoder rerank module
  • Build a small held-out eval set (20–50 scenes) to measure recall@10
  • Route all retrieval through the new pipeline

Phase 3 — Extraction Pass Expansion (1–2 weeks)

  • Add knowledge-state delta pass (writes to knows)
  • Add commitment-extraction pass (writes to commitment)
  • Add scene-segmentation pass (writes to scene)
  • Add multi-granularity summary pass

Phase 4 — Event Sourcing Flip (1–2 weeks)

  • Build materialize_state(chapter_id) worker
  • Treat events as append-only ground truth
  • Generate state snapshots from event log replay

Phase 5 — Continuity Critic (Typed Checks) (2–3 weeks)

  • Entity-mention check (vs. canon)
  • Location/possession consistency check
  • Knowledge-state check (vs. knows)
  • Temporal-consistency check (constraint propagation)
  • Commitment check (foreshadows planted? paid off?)
  • Thread coverage check

Phase 6 — Scene Planner Agent (2–3 weeks)

  • Typed scene plan output: POV, location, time, present characters, threads to advance, commitments to plant/pay off, target word count, target beat
  • Becomes the contract the Drafter satisfies and the Critic verifies against
  • This is the entry point into the agentic generation layer

The Bottom Line

The four critical changes — knows table, bitemporal edges, commitment pool, hybrid retrieval — give us continuity guarantees that no consumer product on the market provides. Together they shift our system from "describes inconsistencies after the fact" to "prevents inconsistencies before commit."

Everything else in the recommendations builds on top of those four. The agentic generation layer, the Scene Planner, the Continuity Critic — all of them assume the knowledge base they query is correct, queryable, and time-aware. Get the schema right first; the agents follow easily.

Treat chapter generation as a database transaction: PLAN → DRAFT → CRITIQUE → REVISE → EXTRACT → COMMIT. No partial state escapes to the next chapter.
